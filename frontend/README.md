## API 연결

`src/shared/api/`는 기존 네 API(상태 확인·연결 확인·세션 생성·특징 전송)와 신규 상품·장바구니·모의 주문 6개 API의 타입·호출 함수를 제공합니다. `contract/frontend-backend.openapi.yaml` 0.4.0에서도 이 형식을 유지합니다. 호출 함수가 있다는 것이 서버 구현 완료를 의미하지는 않습니다. 프론트엔드는 backend와만 통신합니다.

## 주문 API 명세 반영 상태

OpenAPI 0.4.0에 상품 조회, 장바구니 조회·추가·수량 변경·삭제, 모의 주문 확정의 신규 6개 API를 팀 검토용 초안으로 추가했습니다. 요청·응답의 기준 형식은 [OpenAPI](../contract/frontend-backend.openapi.yaml), 설계 이유와 미정 정책은 [주문 API 검토 문서](../docs/Product-Cart-Order-API-Draft.md)를 확인합니다. 신규 operation의 `x-contract-status: draft`는 팀 검토 대기 상태입니다.

주문 operation의 `x-frontend-status: prepared`는 프론트 준비, `x-backend-status: implemented`는 초안 기준 서버 구현 완료를 뜻합니다. 기존 네 연결 API는 백엔드에 구현돼 있으며 상품·장바구니·모의 주문 6개 API는 PR #40에서 초안 기준으로 구현했습니다(메모리 저장). 2026-10-14 실제 백엔드를 연결한 프론트의 주요 주문 흐름·응답 유실 재확인을 검증했습니다. 최종 계약·정책 합의는 별도입니다.

프론트의 상품·Cart·Order 타입·API 호출·화면 처리를 준비했습니다. 성공 응답 후 수량·금액을 확정 표시하고, 네트워크 오류·응답 유실은 같은 키·본문의 ‘주문 반영 확인’으로 재시도합니다. 처리 중에는 변경 버튼을 막습니다. 변경 요청에는 `expected_version`과 `Idempotency-Key`가 필요하며 DELETE의 버전은 쿼리로 전달합니다. 버전 충돌은 최신 장바구니를 표시하고 재확인하며, 신규 오류는 `code`, `detail`, `cart`로 구분합니다. 서버 정책과 초안의 최종 확정은 담당자 리뷰와 팀 합의가 필요합니다.

아래 예시는 기존 연결 API 호출의 사용법입니다.

```ts
import { createBackendApi } from './src/shared/api/index.ts';

// 기존 프록시를 사용합니다. 세션 접근·인증 정책은 백엔드와 별도 합의합니다.
const api = createBackendApi('/backend');
await api.getBackendHealth();
await api.getConnectivity();
const session = await api.createSession();
// 기존 특징 전송 API는 주문 화면에서는 아직 호출하지 않습니다.
const result = await api.sendFeatureWindow(session.session_id, {
  screen_id: 'menu_list',
  window_start: '2026-10-01T10:00:00Z',
  window_end: '2026-10-01T10:00:03Z',
  touch: {
    tap_count: 6, miss_tap_count: 3, repeat_tap_count: 2,
    back_count: 0, dwell_ms: 3000,
  },
  vision: null,
});
```

특징은 화면에서 실제 측정한 1~3초 구간의 통계를 전달해야 합니다. 비전 측정이 없으면 `vision: null`을 사용합니다. `dwell_ms`는 밀리초이며 터치 통계는 0 이상의 정수, 비전 비율·신뢰도와 상태 점수는 0~1입니다.

로컬 파일럿의 `null`(미산출)과 방문 누적 `dwell_ms`는 위 예시의 서버 입력과 별도로 취급합니다. 현재 정수 필드에 `null`을 보내거나 미산출을 0으로 바꾸지 않으며, 의미·계산 담당·전송 정책을 합의한 뒤 연결합니다([터치 로그 검토](../docs/Touch-Log-Review.md#11-프론트-로컬-파일럿-집계-2026-10-25)).

호출자는 `ai_available: false` 또는 `preset: none`이면 화면을 유지하고, `requires_confirmation: true`이면 사용자 수락 후 지원을 적용해야 합니다. 세션이나 화면이 바뀐 뒤 도착한 이전 응답은 적용하지 않아야 합니다. 각 메서드의 마지막 인자로 `AbortSignal`을 전달해 요청을 취소할 수 있습니다.

낮은 화면의 `lowScreen`은 주문 기능의 로컬 화면 설정입니다. 상품·장바구니·주문·특징 API에 이 값을 보내지 않으며 `UIPreset`에도 포함하지 않습니다. `preset: none`은 사용자가 켠 낮은 화면을 포함해 현재 화면을 유지한다는 뜻입니다. 음성·AI에서 높이를 변경하려면 계약의 프리셋·적용 및 복귀 규칙을 팀과 먼저 합의해야 합니다. 높은 화면의 설정·프리셋은 구현 범위에 포함하지 않습니다.

기존 네 API의 HTTP 오류는 `ApiError.status`와 `ApiError.body`로 확인합니다. 기존 특징 API의 422 응답 본문은 명세에 정의되지 않아 원문을 보존합니다. 신규 주문 API의 422는 별도로 `OrderApiError`에 정의했습니다. 네트워크 오류와 요청 취소는 그대로 전달하며 자동 재시도하지 않습니다. 세션·주문 요청은 15초 타임아웃을 사용하고 `ApiError.retryAfterSeconds`로 서버 재시도 간격을 전달합니다. JSON과 HTML·일반 텍스트 오류 모두 숫자 초 단위의 유효한 Retry-After를 보존합니다. API 클라이언트는 응답 전체의 런타임 스키마 검증을 제공하지 않으며 주문 기능에서 완료 응답의 필수 필드·항목·금액·시각을 별도로 검증합니다. 고객 화면에는 서버 내부 오류 상세 대신 상황별 안내를 표시합니다.

검증(Node.js 22.18 이상, 추가 의존성 없음):

```sh
node --test frontend/src/shared/api/client.test.mjs
```

## 실제 백엔드 주문 통합 검증

2026-10-14 PR #43 병합 직후 `main`(`3cb8529`)의 Docker 환경에서 프론트 → Nginx `/backend/` 프록시 → 백엔드로 상품 조회·세션 및 Cart 생성·상품 추가·모의 주문 확정·새 주문 시작을 확인했습니다. 서버는 주문을 처리하고 첫 응답만 유실시킨 경우에도 ‘주문 반영 확인’이 같은 키·본문으로 재요청해 원래 주문번호를 표시했습니다.

상세 근거는 [기존 검증 기록](../backend/README.md#docker-compose)에 있습니다. 고정 응답을 주입한 화면 검사와 별도의 과거 검증 기록이며, 실제 음성 주문·자동 지원 연결이나 G10 실기기 검증을 뜻하지 않습니다.

## 상품·장바구니·주문 화면 실행

React·Vite·TypeScript 주문 화면은 기본 API 모드와 명시적인 개발 샘플 모드를 제공합니다. Node.js 22.18 이상에서 `frontend/`로 이동한 뒤 실행합니다.

```sh
pnpm install
pnpm dev
```

`pnpm build`로 TypeScript 검사와 배포 빌드를, `pnpm test`로 API·주문 상태·터치 로그·개발 샘플·음성 인식·음성 컨트롤러의 여섯 단위 테스트 파일을 실행합니다. 의존성 버전은 `pnpm-lock.yaml`에 기록합니다.

상품 선택·서버 Cart 표시·주문 확인·서버 응답의 샘플 주문번호 표시와 수동 접근성 설정을 제공합니다. 기본 API 모드에는 상품·Cart·Order API를 구현한 백엔드가 필요합니다. 미구현 API의 404에는 연결 대기를 표시하고 로컬 상품·주문으로 대체하지 않습니다. 새 주문·새로고침은 새 세션·빈 장바구니로 시작하며 접근성 설정만 유지합니다. 주문 확인·샘플 주문 완료·새 주문 버튼은 화면 하단에 고정합니다. 상세 동작과 수동 확인 절차는 [`src/features/order/README.md`](src/features/order/README.md)에 있습니다. 실제 결제, 주기적인 특징 전송, 음성 명령의 장바구니 반영 및 자동 지원 판단은 남아 있습니다. 완료 화면 복원·서버 재시작 후 보관·정밀 만료·동적 가격 변경은 후순위입니다.

## 메뉴 화면 음성 입력과 남은 작업

`src/features/voice/`는 Chrome Web Speech API로 한 문장을 듣고 backend 음성 API에 텍스트·인식 후보·현재 화면 ID를 전달합니다. 결과를 조회해 `completed`, `needs_confirmation`, `needs_clarification`, `ignored`, `failed` 상태를 호출자에게 넘기며, 확인·추가 질문이면 대답을 듣기 위해 마이크를 다시 엽니다. 세션 변경·음성 모드 해제 시 진행 중 인식·요청을 취소합니다.

현재 `OrderPage`는 메뉴 화면에서만 음성 모듈을 연결하고 `screen_id=menu_list`를 보냅니다. 인식 중인 문장과 확정 문장·질문·결과·오류를 표시하며 마이크 종료 이벤트를 기다린 뒤 다음 인식을 시작합니다. 주변 대화로 무시된 결과는 표시하지 않고 이전 확인 질문을 유지합니다. 서버가 `failed`를 반환해도 오류를 안내하고 질문·대답 대기를 유지하므로 ‘다시 말하기’에서 짧은 답변을 보낼 수 있습니다. 터치로 장바구니를 저장하는 동안과 저장 후에도 음성 모드를 유지합니다. 화면 이동·모드 해제·세션 변경 또는 주문 연결·상태 오류 시 인식과 요청을 중단합니다. 반환된 `tool_calls` 실행 후 장바구니 동기화, UI 설정 변경·응답 자동 TTS는 남아 있습니다. 별도의 수동 화면 읽기는 로컬 구현에 포함합니다. [화면과 검증 기록](../docs/screenshots/voice-input/README.md)은 모의 응답을 사용하는 검사이며 실제 마이크·OpenAI·G10 확인과 구분합니다.

## 백엔드 없이 프론트 화면 검증

브라우저 테스트는 `src/features/order/orderApiFixture.mjs`의 고정된 HTTP 응답을 주입합니다. 실제 앱에는 이 테스트 응답을 연결하지 않습니다. Vite와 외부 Playwright만 있으면 백엔드 서버 없이 주문 화면·오류·재시도를 확인할 수 있습니다. 개발 서버에 `VITE_ORDER_SAMPLE=true`를 명시하면 기존 17개 상품으로 시연할 수 있습니다. 기본 API 모드는 서버 오류를 샘플로 대체하지 않으며 프로덕션에서는 샘플 설정을 무시합니다. 서버 저장·인증·멱등성을 검증하는 통합 테스트와 구분합니다. [샘플 실행·상세 검증 방법](src/features/order/README.md)을 참고합니다.

## 키오스크 화면 개발 및 검증 기준

전시 대상은 G10의 32인치 세로 디스플레이입니다. 아래 설정은 2026-10-06 프론트엔드 담당 사용자가 제공한 실제 장비의 Windows 디스플레이 설정 화면을 기준으로 합니다. 제품소개서의 32인치 표기만으로 해상도를 추정한 값이 아닙니다.

| 항목 | 개발·전시 기준 |
|---|---|
| 디스플레이 해상도 | 가로 1080 × 세로 1920 픽셀 |
| 화면 방향 | 세로 |
| Windows 배율 | 100% |
| 브라우저 확대율 | 100% (`Ctrl+0`으로 초기화) |
| 실제 장비 확인 모드 | 브라우저 F11 전체 화면 |
| 개발 PC 미리보기 | Chrome·Edge의 F12 기기 모드에서 Responsive 1080 × 1920 |

프론트 UI를 구현하거나 수정할 때는 이 세로 화면을 기본 검증 크기로 사용합니다. 개발 PC의 가로 모니터에서 F11만 누른 화면은 가로 해상도를 그대로 사용하므로 전시 배치의 기준이 아닙니다. 기기 미리보기의 `Fit to window`는 세로 화면을 개발 PC에 맞춰 축소해 보여주는 표시 옵션입니다.

### 확인 절차

1. `pnpm dev`로 주문 화면을 실행하고 브라우저 확대율을 100%로 맞춥니다.
2. 개발 PC에서는 F12 → `Ctrl+Shift+M` → Responsive에서 가로 1080, 세로 1920을 설정합니다. F12 도구를 단순히 옆에 열어 둔 화면 대신 지정한 기기 화면 크기로 확인합니다.
3. 상품 목록·분류, 옵션 창, 장바구니, 주문 확인·완료의 잘림·겹침·가로 넘침과 필요한 세로 스크롤을 확인합니다. 스크롤 후에도 주요 조작에 접근할 수 있어야 합니다.
4. 큰 글씨(200%)·큰 버튼을 각각 켜고 함께 적용한 상태도 확인합니다. 고대비를 켜고 끄며 문자·선택 상태를 확인하고, 옵션 선택·수량 조절·담기·주문 확인 버튼을 실제로 조작합니다.
5. 하단의 ‘낮은 화면’으로 전환하고 기본·큰 글씨·큰 버튼·전체 설정 적용 상태를 확인합니다. 1080×1920에서는 조작 영역이 y=768부터 높이 1152px이며, 목록·장바구니는 내부 스크롤로 끝까지 접근하고 옵션 창도 아래에 열려야 합니다. 짧은 창에서는 최소 720px을 확보하되 창 높이를 넘지 않습니다.
6. 하단 주문 확인·샘플 주문 완료·새 주문·화면 높이 전환 버튼의 위치와 겹침을 확인합니다. 목록 끝이 하단 고정 영역 위까지 스크롤돼야 합니다. 개발용 로그 버튼은 주문 영역 위에 두며 펼친 창과 접은 창에서 모두 확인합니다. 기본 높이·낮은 화면 모두에서 터치 좌표·대상 경계와 문서 또는 내부 컨테이너의 스크롤 기록을 확인합니다.
7. ‘기본 높이’ 전환 후 담은 메뉴와 다른 설정이 유지되는지, 새 주문·새로고침 후 낮은 화면·고대비가 유지되는지, ‘기본 화면’이 모든 화면 설정을 초기화하는지 확인합니다. ‘처음으로’에서 취소하면 기존 장바구니가 유지되고 확인하면 새 세션으로 시작하는지 확인합니다. 화면 읽기의 중단·다시 읽기와 음성 입력 전환도 검사합니다.
8. 실제 장비에서는 Windows 해상도·방향·배율을 다시 확인하고, 브라우저 확대율 100%·F11 전체 화면에서 최종 검증합니다. 폰트·스크롤바·브라우저 차이와 낮은 화면의 실제 도달 범위를 확인하고 실제 화면의 스크린샷과 결과를 PR에 첨부합니다.

화면 크기는 물리적인 인치 수와 별개입니다. 배치가 예상과 다르면 브라우저 콘솔의 `window.innerWidth`, `window.innerHeight`, `window.devicePixelRatio`로 실제 뷰포트·배율 정보를 확인해 검증 결과에 남깁니다. 실제 장비의 화면 설정이 달라지면 변경 내용을 공유하고 이 기준도 갱신합니다.

### 새 주문의 화면 설정과 스크린샷

2026-10-11 프론트 담당자 검토 방향으로 새 주문·수동 재시작·새로고침에도 화면 설정을 유지합니다. ‘화면 도움 → 기본 화면’으로 사용자가 직접 초기화합니다. 다음 이용자에게 자동 초기화할지 여부와 공용 단말의 설정 보관 정책은 팀 합의 대기이며 서버 세션 정책과 구분합니다.

2026-10-13 추가한 낮은 화면과 2026-10-25 로컬 변경의 고대비도 이 유지 정책을 따릅니다. 하단의 ‘기본 높이’는 `lowScreen`만 해제하며 ‘기본 화면’은 큰 글씨·큰 버튼·간편 화면·단계별 안내·고대비까지 모두 초기화합니다. 저장 키는 기존 `kiosk-ui-settings-v1`을 사용하고, 이전 설정에 `lowScreen`·`highContrast`가 없으면 각각 `false`로 시작합니다. [낮은 화면의 기존 검증 기록](src/features/order/README.md#낮은-화면)과 [로컬 변경의 검증 방법](src/features/order/README.md#검증-실행)을 구분합니다. 화면 읽기·누름 소리는 저장하는 화면 설정에 포함하지 않으며 새로고침 시 꺼집니다.

UI 검증 이미지는 `docs/screenshots/<기능>/`에 필요한 대표 화면만 보관하고 PR 본문에 첨부합니다. 모든 자동 검사 결과는 저장소에 넣지 않습니다. [주문 화면 스크린샷 기준](../docs/screenshots/order-api/README.md)에서 크기·모드·검증 범위와 실제 장비 확인 여부를 기록합니다. 이는 프론트 담당자의 현재 운영 방향이며 팀 전체의 영구 보관 정책 합의를 뜻하지 않습니다.

## Docker 실행과 백엔드 연결

Docker Desktop의 Linux 엔진과 WSL 통합을 활성화한 뒤 저장소 루트에서 실행합니다.

```sh
docker compose up --build -d
curl --fail http://127.0.0.1:8080/backend/health
```

화면은 `http://127.0.0.1:8080`에서 열립니다. 상태 확인 응답은 `{"status":"ok","service":"backend"}`입니다. 이는 백엔드 프로세스 상태만 확인하며 DB·AI 연결을 보장하지 않습니다.

프론트 이미지는 Node.js에서 빌드한 정적 파일을 Nginx로 제공합니다. 브라우저의 `/backend/health` 요청은 Nginx가 Docker 내부 `http://backend:8000/health`로 전달합니다. `/backend/api/v1/...`도 같은 방식으로 전달하며 백엔드 오류 응답을 그대로 반환합니다. 화면 경로는 `index.html`로 처리합니다.

화면 코드에서 기본 프록시 클라이언트를 사용할 수 있습니다.

```ts
import { backendApi } from './src/shared/api/index.ts';

const health = await backendApi.getBackendHealth();
```

백엔드에는 `/health`, 연결 확인, 임시 세션 생성, 특징 전송이 구현돼 있습니다. 상품·장바구니·모의 주문 6개 API도 PR #40에서 초안 기준으로 구현됐으며, 실제 백엔드를 연결한 프론트 주문 흐름은 [2026-10-14 기록의 범위](#실제-백엔드-주문-통합-검증)에서 검증했습니다. 공개 환경의 세션 접근·인증·쿠키·CORS 정책은 백엔드 담당자와 합의할 사항입니다. 프론트 작업에서 서버 설정을 변경하지 않습니다.

로컬 `pnpm dev`도 `/backend/`를 `http://127.0.0.1:8000`으로 전달합니다. 다른 백엔드에 연결하려면 `BACKEND_URL=http://127.0.0.1:8000 pnpm dev`처럼 실행 환경에서 주소를 전달합니다. Docker에서는 Compose의 frontend `BACKEND_URL` 환경변수로 대상 주소를 설정합니다. 주소는 브라우저에 Docker 서비스 이름을 노출하지 않고 프록시에서 사용합니다.

종료는 저장소 루트에서 `docker compose down`으로 합니다.
