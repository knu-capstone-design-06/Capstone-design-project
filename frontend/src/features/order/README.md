# 상품·장바구니·모의 주문 화면

현재 OpenAPI 0.4.0 초안에 맞춰 상품 표시·서버 Cart 표시·주문 확인·서버 응답의 주문번호 표시를 구현했습니다. 2026-10-14 Docker에서 실제 백엔드를 연결한 프론트의 주요 주문 흐름·응답 유실 재확인을 검증했습니다. [검증 범위](../../../README.md#실제-백엔드-주문-통합-검증)와 [주문 API 검토 문서](../../../../docs/Product-Cart-Order-API-Draft.md)를 참고합니다. 이 화면 검증은 팀 전체의 최종 계약 합의와 구분합니다.

- 기본 API 모드는 상품 가격·Cart 항목·총액에 서버 응답을 사용합니다. 개발용 샘플은 아래 설정으로 명시적으로 켤 수 있습니다.
- 추가·수량 변경·삭제는 성공 응답 뒤 확정 표시하고 요청 중 변경을 막습니다. 첫 시연 정책의 항목별 20개 한도를 화면에 적용했습니다.
- 응답 유실은 같은 키·버전·본문으로 ‘주문 반영 확인’을 실행합니다. 충돌은 최신 Cart를 표시하고 재조작에 새 키를 사용합니다.
- 재확인에도 실패하면 ‘처음부터 다시 주문’으로 대기 요청을 버리고 새 서버 세션을 시작할 수 있습니다. 첫 실패나 요청 처리 중에는 이 기능을 제공하지 않습니다. 장바구니 변경은 새 장바구니 시작과 이전 변경 결과 미확인을 안내하고, 주문 확정은 이전 샘플 주문이 자동 취소되지 않는다는 안내를 표시합니다.
- 변경 요청의 코드 없는 404·410과 세션·접근 오류는 새 이용 시작을 안내합니다. 상품·장바구니 항목 없음 404는 기존 주문을 유지하고, 초기 주문 API 미구현은 연결 대기로 표시합니다.
- 처리 중 오류의 코드·보관 정책은 백엔드와 합의할 항목입니다. 서버의 409 + Retry-After가 있으면 수동 재시도 간격을 지킵니다.
- JSON·HTML·일반 텍스트 오류에서도 유효한 숫자 초 단위 Retry-After를 보존합니다. 잘못된 값이나 음수는 간격으로 적용하지 않습니다.
- 주문번호는 서버 응답을 그대로 표시합니다. 프론트에서 번호를 발급하거나 서버 완료 상태를 저장하지 않습니다.
- 주문 성공 응답의 필수 필드·항목·수량·금액·생성 시각을 검증합니다. 불완전하거나 세션이 다르면 장바구니를 유지하고 같은 키·본문으로 결과를 다시 확인합니다.
- 완료 후 새 이용과 새로고침은 기존 세션 생성 API로 새 세션을 요청합니다. 접근성 설정만 로컬에 유지합니다.
- 기존 main의 세션 API를 사용하며 별도 백엔드 라우터·Cart 서비스·인증·저장소를 구현하지 않습니다.
- 상품·Cart·Order API가 없는 서버에서는 연결 대기를 표시합니다. 현재 main에는 PR #40의 초안 기준 주문 API 6개가 구현돼 있으며, 실제 백엔드를 연결한 프론트 주문 흐름은 [기존 검증 기록](../../../README.md#실제-백엔드-주문-통합-검증)의 범위에서 확인했습니다.
- 메뉴 화면의 음성 버튼은 `../voice/`의 Chrome 인식·backend 음성 요청·상태 조회 모듈에 연결했습니다. 주문 확인·완료 화면으로 이동하거나 세션을 바꾸면 진행 중인 인식과 요청을 중단합니다. 음성 해석 결과의 주문 실행·MCP·장바구니 동기화·실제 결제·재고 차감은 연결하지 않았습니다. 복원·장기 보관·정밀 만료·동적 가격은 후순위입니다.

큰 글씨(200%)·큰 버튼·간편 화면·단계별 안내·낮은 화면·고대비와 로컬 터치 기록을 제공합니다. 2026-10-25 로컬 구현의 화면 읽기·누름 소리·파일럿 집계는 아래 별도 절에 기록합니다. 새 서버 세션을 받을 때 로컬 로그도 새 세션으로 분리하고 시작 기록의 `server_session_id`와 각 이벤트의 `serverSessionId`에 연결 ID를 남깁니다. 새로고침은 이전 기록 버퍼를 보관하되 이전 세션을 이어 쓰지 않습니다. 연결 전·재연결 대기의 기록은 서버 ID가 null인 별도 로컬 세션입니다. 이 경계는 프론트 담당자의 작업 방향이며 팀의 서버 만료·복원 정책 합의를 뜻하지 않습니다.

개발 확인 창의 원시 로그 요약·화면 방문별 표·`window.kioskTouchLogDraft.summarize()`는 [PR #50](https://github.com/knu-capstone-design-06/Capstone-design-project/pull/50)으로 2026-10-19 main에 병합했습니다. 현재 창은 보관 중인 현재 세션의 원시 기록 요약·대상 밖 비율·화면 방문별 표·최근 기록 20개·JSON 내보내기를 제공합니다. [요약 범위](#개발용-원시-터치-로그-요약)는 서버용 통계와 구분하며, 반복·주변 거리·`dwell_ms` 등의 통계 기준과 서버 전송은 [터치 로그 검토 문서](../../../../docs/Touch-Log-Review.md)의 합의 항목으로 남아 있습니다.

개발 모드의 `큰 글씨 + 큰 버튼`은 기존 두 설정을 한 번에 켜거나 끄는 비교용 옵션입니다. 운영 빌드에서는 개별 설정만 표시합니다. 둘 중 하나만 켜져 있으면 두 설정을 모두 켜고, 둘 다 켜져 있으면 모두 끕니다. 개별 옵션은 그대로 사용할 수 있고, 두 설정이 모두 켜져 있을 때만 통합 버튼이 선택 상태로 표시됩니다. 별도의 설정 필드 없이 기존 저장·복원과 로컬 설정 변경 기록을 사용합니다.

### 낮은 화면

하단 주문 바의 ‘낮은 화면’ 또는 ‘화면 도움 → 낮은 화면’으로 켭니다. 1080×1920 기준으로 화면 아래쪽 60%(1152px)에 화면 도움·메뉴·장바구니·주문 진행 버튼을 배치하고, 옵션 창도 아래에 엽니다. 목록과 긴 주문 내역은 이 영역 안에서 스크롤합니다. 짧은 창은 조작 영역을 최소 720px까지 확보하되 창 높이를 넘지 않게 합니다.

‘기본 높이’는 화면 높이만 되돌립니다. 큰 글씨·큰 버튼·간편 화면·단계별 안내·고대비와 함께 사용할 수 있고, 높이 전환은 담은 메뉴를 유지합니다. 기존 화면 설정과 같이 새 주문·새로고침에도 유지하며 ‘기본 화면’은 모든 화면 설정을 초기화합니다. 이전 저장 데이터에 `lowScreen`이 없으면 기본 높이를 사용합니다.

높은 화면 모드는 2026-10-14 프론트 담당자의 요청에 따라 현재 구현 범위에서 제외하며 구현하지 않습니다. 화면 높이는 기본 높이와 낮은 화면만 제공합니다.

`lowScreen`은 기존 localStorage 키 `kiosk-ui-settings-v1`에 불리언으로 저장합니다. 높이 전환은 서버 요청·새 세션·새 화면 방문을 만들지 않으며, 기존 터치 기록의 `settings`와 `ui_settings_change`에 변경을 남깁니다. 좌표는 낮은 영역의 원점으로 바꾸지 않고 전체 뷰포트 기준 CSS 픽셀을 사용합니다. [터치 로그 설명](../../../../docs/Touch-Log-Review.md#10-낮은-화면-추가에-따른-기록검증-범위)을 참고합니다.

프론트 담당자가 요청한 수동 화면 기능입니다. `contract/`의 서버 프리셋 추가나 AI 자동 지원 연결을 뜻하지 않으며, 실제 G10의 도달 범위는 Windows·브라우저 100% 배율과 F11 전체 화면에서 최종 확인해야 합니다.

2026-10-13 단위 테스트 37개, TypeScript 검사·Vite 빌드, Chrome 브라우저 검사 64개를 확인했습니다. 브라우저 검사에는 낮은 화면의 1080×1920·1920×1080·1365×768·390×844 × 기본·큰 글씨·큰 버튼·전체 설정 적용 16개 조합과 기존 주문·터치 로그 회귀 검사를 포함합니다. 고정 API 응답·개발 샘플로 검증했으며, 샘플 설정으로 빌드한 운영 화면의 샘플 차단도 별도로 확인했습니다.

## 개발용 원시 터치 로그 요약

2026-10-17 프론트 담당자 요청으로 기존 개발용 ‘터치 로그 보기’ 창에 현재 로컬 세션의 원시 기록 요약을 추가했습니다. 누름 시작, 활성·비활성 버튼/링크 안 누름, 대상 밖 누름, 손 뗌·취소·중단, 스크롤 관측, 화면 진입, 분류·옵션·UI 설정 변경의 기록 수를 표시합니다. 화면 방문별 표는 같은 화면의 재방문을 별도 행으로 구분하며, 행 번호는 보관 기록에서 나타난 순서입니다.

대상 밖 비율은 `대상 밖 pointer_start 수 / 현재 세션의 보관 중인 모든 pointer_start 수`입니다. 누름이 없거나 대상 정보가 빠진 기록이 있으면 비율은 `null`로 두고 화면에 산출하지 않은 이유를 표시합니다. 누락된 대상 정보는 영역 밖으로 추정하지 않고, 취소 여부가 없는 종료 기록도 별도로 셉니다. 비활성 대상은 대상 밖 입력에 포함하지 않습니다.

계산 범위는 최신 1,000개 버퍼 안에 남은 현재 로컬 세션 기록입니다. 이전 세션은 합산하지 않으며 시작 기록이 없으면 세션 전체 수치로 해석하지 않도록 안내합니다. 각 수치는 이벤트 기록 수이므로 시작 기록 없이 종료만 남을 수 있고, 스크롤 이벤트 여러 개가 한 제스처에서 발생할 수도 있습니다. 대상 밖 입력을 실패, 손 뗌을 완료 탭이나 조작 성공, 스크롤 관측 수를 스크롤 의도 횟수로 해석하지 않습니다. 낮은 화면 상단 안내 영역은 기존 수집 범위 밖입니다.

로컬 요약은 `contract/`의 `TouchFeatures`나 팀의 통계 정책을 확정한 것이 아닙니다. 2026-10-25 추가한 반복·전경 체류·뒤로가기 로컬 파일럿은 아래 별도 절에 정의합니다. 주변 입력, 성공·실패 판정, 재방문 통계, 시스템 대기 시간과 서버 전송은 [터치 로그 검토 문서](../../../../docs/Touch-Log-Review.md)의 T01~T14 합의 후 연결합니다. 원시 수집·보관 형식과 JSON 내보내기 형식은 유지합니다.

```js
window.kioskTouchLogDraft.summarize(); // 현재 세션 원시 기록 요약 복사본
window.kioskTouchLogDraft.read();      // 원시 기록 버퍼 복사본
```

요약 창은 개발 빌드에서만 표시하며, 확인 창의 입력·스크롤은 수집에서 제외합니다. 표시 일시정지는 수집을 멈추지 않고 요약과 최근 기록의 갱신만 멈춥니다. 단위 테스트는 기존 `npm test`의 `touchLog.test.mjs`, 화면 검사는 기존 `touchLog.browser.test.mjs`에 포함합니다.

검증(2026-10-17): Windows Node.js 24.21.0의 `npm test` 62개, 기존 의존성을 사용한 WSL Node.js 24.15.0의 `npm run build`(TypeScript·Vite) 통과. Windows Chrome headless의 터치 로그 브라우저 검사 34개와 운영 빌드의 개발 도구 숨김을 포함한 별도 검사 1개가 통과했습니다. 고정 API 응답을 사용했으며 실제 G10·스크린리더·서버용 통계는 검증 범위에 포함하지 않습니다. [대표 화면과 검증 범위](../../../../docs/screenshots/touch-log-summary/README.md)를 참고합니다.

## 고객 안내와 주요 조작 위치

### 메뉴 화면 음성 입력

2026-10-15 프론트 담당자 요청으로 음성 모드 버튼을 추가했습니다. 2026-10-25 로컬 개선에서는 ‘켜짐/꺼짐’과 음소거 아이콘·선택 테두리로 상태를 구분하며, ON/OFF 문구와 상태등 맥동을 제거했습니다. 버튼의 `role="switch"`·`aria-checked`와 Enter·Space 전환은 유지합니다.

버튼의 접근성 이름은 ‘음성 모드’이며 버튼 밖의 마이크 안내를 `aria-describedby`로 연결했습니다. ON/OFF는 `aria-checked`로 전달하고, 인식·처리·질문·오류 문구는 별도의 `role="status"` 영역에 표시합니다. 실제 스크린리더 음성 출력 확인은 별도로 남아 있습니다.

API 모드에서 메뉴 화면의 버튼을 켜면 Chrome 마이크로 한 문장을 듣고 `screen_id: menu_list`로 backend 음성 API에 전송합니다. Chrome이 인식한 문장은 처리 결과가 나온 뒤에도 화면에 표시하며, 모드를 끄거나 세션이 바뀌면 지웁니다. 주문 요청이 아닌 주변 대화로 무시된 문장은 남기지 않습니다. 답변이 필요하면 모듈이 마이크를 다시 열고, 그 밖의 결과나 무음 종료 뒤에는 ‘다시 말하기’로 재시작합니다. 버튼을 끄거나 주문 확인·완료로 이동하거나 새 세션을 시작하면 인식·요청을 중단합니다. Chrome 인식 미지원, 권한 거부, 요청 실패는 안내하고 터치 주문은 계속 사용할 수 있습니다. 음성 모드는 저장하지 않으며 메뉴 화면에 다시 들어오면 꺼짐으로 시작합니다.

#### 개발 샘플의 음성 인식 테스트 (2026-10-25)

`VITE_ORDER_SAMPLE=true`인 개발 서버에서는 같은 버튼이 **음성 인식 테스트**로 표시됩니다. 추가 환경변수·백엔드·OpenAI 키 없이 Chrome의 브라우저 인식으로 중간 문장과 확정 문장을 확인합니다. 한 문장 뒤 마이크를 닫고 ‘다시 말하기’로 재시도합니다. 짧은 말과 낮은 신뢰도도 표시하며 주문·장바구니는 바꾸지 않습니다. 이 경로는 프로젝트의 backend 요청·상태 조회·결과 콜백을 실행하지 않습니다.

인식 미지원과 마이크 권한 거부는 안내하고, 끄기·화면 이동·새 세션에서는 인식을 중단하고 이전 문장을 지웁니다. 화면 읽기와 마이크의 동시 재생 방지는 기존 음성 상태를 공유합니다. 인식 문장은 별도 저장하지 않습니다. 브라우저의 음성 인식 서비스에는 마이크 권한과 네트워크가 필요할 수 있으며 오프라인 인식을 보장하지 않습니다. API 모드는 기존 서버 해석을 사용하고 프로덕션 빌드는 개발 샘플 테스트를 노출하지 않습니다.

위의 개발 샘플 실행 방법으로 서버를 켠 뒤 Vite가 출력한 주소를 사용합니다. 브라우저 검증 시 그 주소를 `ORDER_SAMPLE_BROWSER_URL`에 지정하면 실제 backend 호출이 없는지 모의 인식기로 확인합니다. 실제 마이크 인식 품질은 별도 확인합니다.

2026-10-21 재점검에서 Chrome 종료 이벤트 전 재시작 충돌, 주변 대화 뒤 확인 질문 소실, 질문에 답하는 중간 인식 문장 누락을 수정했습니다. `ignored` 결과는 표시하지 않으며 이전 질문에 대한 대답 대기를 유지합니다. 주변 대화 뒤에는 ‘다시 말하기’로 재개할 수 있습니다. 비동기 마이크 종료·빠른 OFF/ON·중단된 재시작의 회귀 테스트와 Chrome 화면 검사 3개를 추가·확인했습니다. 실제 발화 인식과 외부 AI 호출은 검증하지 않았습니다.

2026-10-22 PR #53 리뷰를 반영해 서버의 `failed` 응답 뒤에도 이전 확인·추가 질문과 대답 대기를 유지합니다. 실패 안내 후 ‘다시 말하기’를 누르면 이전 질문을 다시 표시하고 ‘네’ 같은 짧은 답변도 전송합니다. 질문 없이 실패한 경우에는 대답 대기를 새로 만들지 않습니다. 터치로 상품 추가·수량 변경·삭제를 저장하는 `saving` 상태에서도 음성 모드·인식기를 유지하고 모드를 끌 수 있습니다. 주문 연결·상태 오류(`uncertain`, `disconnected`, `ended` 등)에서는 모드를 끄며, 주문 확인·완료 이동과 세션 변경의 종료 동작도 유지합니다.

현재 같은 메뉴 화면의 식별자는 음성 API에서 `menu_list`, 로컬 터치 로그에서 `menu`입니다. 두 값은 같은 화면을 가리키며, 현재 전송 코드와 로그 이름을 유지한 대응 관계입니다. 두 기록의 서버 결합·계약 식별자 통일은 별도 합의 대상입니다.

음성 API의 `completed`는 해석 완료입니다. 현재 backend는 `tool_calls`를 실행하지 않으므로 장바구니가 바뀌었다고 안내하지 않습니다. 주문 확인 화면의 `screen_id`와 도구 실행·결과 동기화 방식은 팀 합의 후 연결합니다. [연결 화면 검증](../../../../docs/screenshots/voice-input/README.md)과 [기존 버튼 미리보기 검증](../../../../docs/screenshots/voice-button/README.md)을 구분해 기록합니다.

### 주문 진행 안내

주문 확인·샘플 주문 완료·새 주문 버튼과 금액을 화면 하단에 고정합니다. 목록 끝은 하단 영역 위까지 스크롤할 수 있고 개발용 로그 버튼은 주문 영역 위에 둡니다. 주문 시작 시 메뉴 화면으로 먼저 전환해 새 서버 세션에 이전 완료 화면의 방문 기록을 남기지 않습니다.

고객 문구는 해요체로 통일하고 장식용 영문은 제거했습니다. 샘플 표시와 실제 결제가 없다는 설명은 유지합니다. 고객 오류 안내는 `copy.ts`에서 관리하며 서버 오류 본문·HTTP 코드·내부 상태를 그대로 표시하지 않습니다. 단계별 안내는 한 줄에 한 행동씩 구분합니다.

실패 안내가 새로 나타나면 안내와 재확인 버튼을 화면 안으로 스크롤합니다. 옵션 창 안의 오류도 같은 방식으로 처리합니다. 주문 응답 검증 실패는 개발 환경의 콘솔에 `order_number`, `items[0].temperature` 같은 필드 경로만 기록하며 서버 응답 값은 출력하지 않습니다. 불완전한 응답의 장바구니 유지와 같은 요청 재확인 방식은 유지합니다.

2026-10-11 프론트 담당자가 새 주문·재시작·새로고침에서도 화면 설정을 유지하는 방향을 승인했습니다. ‘화면 도움 → 기본 화면’은 사용자가 명시적으로 초기화하는 동작입니다. 이용자 전환 시 자동 초기화와 공용 단말의 보관 정책은 팀 합의 대기입니다.

## 개발용 샘플 모드

백엔드 없이 화면을 시연할 때는 개발 서버 실행 시에만 샘플 응답 어댑터를 선택합니다.

`$env:VITE_ORDER_SAMPLE`은 PowerShell의 현재 프로세스에 환경변수를 설정하는 문법입니다. Vite가 `VITE_`로 시작하는 변수를 `import.meta.env`로 전달하고, `OrderPage.tsx`가 개발 서버인지(`DEV`)와 값이 `true`인지 확인해 샘플 어댑터 또는 실제 백엔드 API를 선택합니다. Vite의 기본 개발·운영 모드와 별개로 이 프로젝트가 정한 샘플 주문 선택 옵션이며, 음성 버튼 ON/OFF와도 별개입니다.

```powershell
$env:VITE_ORDER_SAMPLE='true'
pnpm dev
```

화면에 ‘개발용 샘플 · 실제 결제 없음’을 표시하고 기존 17개 상품으로 옵션·수량·삭제·확인·완료·새 주문을 시연합니다. 개발 어댑터는 HTTP 응답과 같은 형태의 메모리 샘플을 제공합니다. `/backend/` 요청·서버 저장·실제 결제는 발생하지 않으며 주문번호는 `DEV-SAMPLE-`으로 구분합니다. 새로고침하면 샘플 주문 상태도 초기화합니다.

`VITE_ORDER_SAMPLE`을 지우거나 `false`로 설정하고 개발 서버를 다시 시작하면 기본 API 모드로 돌아갑니다. 서버 오류가 발생했다고 자동으로 샘플 모드로 전환하지 않습니다. 프로덕션 빌드·Docker 실행에서는 이 값이 `true`여도 샘플 어댑터를 사용하지 않습니다. 설정을 프로젝트의 `.env`에 저장하거나 새 의존성을 추가할 필요는 없습니다.

PowerShell에서 기본 API 모드로 돌아갈 때는 실행 중인 서버를 `Ctrl+C`로 종료한 뒤 아래 명령을 실행합니다. 실제 백엔드가 필요합니다.

```powershell
$env:VITE_ORDER_SAMPLE='false'
pnpm dev
```

이 설정은 현재 PowerShell 창과 여기서 실행한 개발 서버에만 전달됩니다. 창을 닫거나 컴퓨터를 재부팅하면 사라지므로 새 창에서 샘플 모드를 쓸 때 다시 설정합니다.

## 백엔드 없이 화면 검증

외부 Playwright 모듈을 제공하고 Vite를 실행합니다. 서비스 의존성에 Playwright를 추가하지 않습니다.

```powershell
$env:PLAYWRIGHT_MODULE='file:///절대경로/playwright/index.mjs'
$env:PLAYWRIGHT_CHANNEL='msedge'
$env:ORDER_BROWSER_URL='http://127.0.0.1:5173'
node --test src/features/order/order.browser.test.mjs
$env:TOUCH_LOG_BROWSER_URL=$env:ORDER_BROWSER_URL
node --test src/features/order/touchLog.browser.test.mjs
node --test src/features/order/touchLog.test.mjs
node --test src/features/order/sampleOrderApi.test.mjs
```

`PLAYWRIGHT_CHANNEL`을 지정하지 않으면 설치된 Microsoft Edge(`msedge`)로 실행합니다. 설치된 Google Chrome은 `chrome`, Playwright가 관리하는 Chromium은 `default`로 선택합니다. `default`는 실행 채널을 생략하므로 해당 Playwright 버전의 Chromium 브라우저가 미리 설치돼 있어야 합니다. 주문·터치 로그 테스트에 같은 설정을 사용합니다.

샘플 모드를 켠 별도 개발 서버를 `ORDER_SAMPLE_BROWSER_URL`, 빌드 후 `pnpm preview`로 연 화면을 `ORDER_PRODUCTION_URL`에 지정하면 추가 브라우저 테스트 2개를 실행합니다. 두 URL을 지정하지 않으면 해당 테스트만 생략합니다. 예: `$env:ORDER_SAMPLE_BROWSER_URL='http://127.0.0.1:5180'`, `$env:ORDER_PRODUCTION_URL='http://127.0.0.1:5181'`. 기본 API 모드 테스트의 `ORDER_BROWSER_URL`에는 샘플을 끈 서버를 지정합니다.

`orderApiFixture.mjs`는 요청 순서·내용을 확인하고 미리 준비한 HTTP 응답만 전달합니다. 실제 앱에서 import하지 않으며 서버 상품 공급·옵션 검증·Cart 변경·주문번호 발급 로직을 구현하지 않습니다.

2026-10-11 프론트 상태/API 25개, 로컬 터치 기록 6개, 개발 샘플 3개로 단위 테스트 총 34개와 TypeScript/Vite 빌드를 확인했습니다. Edge·Chrome에서 브라우저 검사 각각 27개가 모두 통과했습니다. 주문 검사에는 12개 화면·접근성 조합의 하위 검증을 포함하고 터치 기록 검사 3개를 함께 실행했습니다. 샘플·프로덕션 URL도 지정해 해당 검사를 생략하지 않았습니다. 서버 실제 동작에 대한 검증 결과는 아닙니다.

2026-10-12 단위 테스트 36개(API 8·주문 상태 19·터치 로그 6·개발 샘플 3), TypeScript/Vite 빌드와 Edge·Chrome의 브라우저 검사 각각 47개(주문 31·터치 로그 16)를 확인했습니다. 샘플·프로덕션 검사도 생략하지 않았습니다. 하단 바 가림 검사는 3개 해상도 × 기본·큰 글씨·큰 버튼·동시 적용 12개 조합, 긴 주문 내역의 오류 안내 검사는 3개 해상도 × 기본·동시 적용 6개 조합입니다. 주문 응답 필드 진단과 장바구니 변경의 재확인 문구도 확인했습니다.

| `order_state_change` | 화면이 관측한 주문 상태·완료 여부·안내 표시 여부와 장바구니 버전·상품/항목 ID·온도·수량의 변경 전후 값 |
| `selection_state_change` | 열린 상품 옵션의 상품 ID·온도·수량 변경 전후 값. 옵션이 닫히면 `after: null` |
| `voice_state_change` | 음성 모드·실제 마이크 활성 여부·처리 단계의 변경 전후 값. 인식 문장·서버 응답·오류 상세는 수집하지 않음 |
| 포인터 지속·동시 입력 | 시작·종료·중단에 `pointerId`와 `overlappingInputIds`, 종료·중단에 `durationMs`. 지속 시간은 `performance.now()`의 차이이며 중단 시에는 중단까지 관측한 시간 |

상태 이벤트는 값이 바뀌었을 때와 새 로컬 세션의 기준선을 기록할 때만 추가합니다. 새 세션의 첫 상태는 `before: null`이며 이전 세션의 장바구니·옵션을 변경 전 값으로 이어 붙이지 않습니다. 같은 세션에서도 첫 관측 또는 닫힌 옵션의 `null`을 실제 빈 장바구니와 구분합니다. 보관 버퍼에서 오래된 기록이 빠지면 전체 변화 과정을 복원하지 못할 수 있습니다.

예를 들어 담기 요청 중에는 `status: saving`과 기존 장바구니를 기록하고, 서버 응답으로 수량이 바뀌면 새 장바구니를 기록합니다. 이는 React 화면이 관측한 상태 변화이며 HTTP 요청별 실행 결과·지연 시간이나 특정 입력과 성공의 인과관계를 확정하는 기록은 아닙니다. 현재 UI는 옵션 기본값을 미리 선택하므로 선택 기록만으로 사용자의 선택 완료 의도를 판정하지 않습니다.

동시 접촉이 관측된 누름은 로컬 `repeat_tap_count`의 단일 반복 후보에서 제외합니다. 접촉 정보는 핀치 의도를 확정하지 않으며, 탭·두 번 탭·길게 누름·드래그·핀치의 분류 기준은 아직 추가하지 않았습니다. 카테고리 이동은 기존 `category_change`로 기록하고 `back_count`는 기존 주문 확인 → 메뉴 이동 정의를 유지합니다. 새로고침의 새 세션·접근성 설정 유지와 서버 계약·전송 동작도 기존 기준을 따릅니다.

2026-10-29 Windows Node.js 24.21.0에서 단위 테스트 81개, Chrome headless 브라우저 검사 105개(하위 검사 포함, 생략 0개), TypeScript·Vite 빌드와 `git diff --check`가 통과했습니다. 추가 검사는 1080×1920 기본·200% 확대·낮은 화면의 저장 대기·수량 정정·새 세션 상태 분리, 동시 접촉·취소·중단과 인식문 미수집을 확인합니다. 고정 API 응답·모의 음성 인식·합성 포인터 입력을 사용했으며 실제 G10·서버·마이크 확인은 별도입니다.

## 2026-10-25 로컬 파일럿: 터치 집계와 PR #55 반영

이번 변경은 로컬 검토용입니다. 원격 푸시·PR 게시, 서버 통계 전송, 자동 지원 판단은 하지 않습니다. 기존 원시 JSON 형식은 유지하고 입력 방식(`pointerType`, `isPrimary`)과 화면 진입 시 전경 여부, `visibility_change` 기록을 추가합니다. 이전 기록의 누락 필드는 추측해 보충하지 않습니다.

### 터치 집계

2026-10-25 로컬 코드에 적용한 파일럿 시작 기준입니다. 팀 전체의 T01~T14 계약 합의와 구분합니다. `touchLogFeatures.ts`에서 계산하며 개발용 터치 로그 창과 `window.kioskTouchLogDraft.features()`로 확인합니다.

| 필드 | 로컬 파일럿 정의 |
|---|---|
| `tap_count` | 현재 로컬 세션의 최근 2초 `(시작, 끝]`에 관측한 `pointer_start` 수. 손 뗌·조작 성공 횟수가 아님 |
| `miss_tap_count` | 같은 구간의 `data.target === null` 누름. 비활성 대상·정보 없는 대상은 영역 밖으로 추정하지 않음 |
| `repeat_tap_count` | 같은 방문·입력 방식·대상에서 인접한 누름의 간격이 **800ms 이하**, 시작 좌표 간 거리가 **24 CSS px 이하**인 추가 누름 수. 두 입력 모두 손 뗌을 관측하고 이동이 24px 이하여야 함. 취소·중단·시간상 연결된 스크롤·다른 방문은 제외 |
| `back_count` | 같은 구간에서 `review`에서 `menu`로 이동한 `screen_enter` 수. 새 세션의 첫 방문은 뒤로가기가 아님 |
| `dwell_ms` | **현재 화면 방문의 전경 체류 누적 시간**. 백그라운드·페이지 중단은 제외. 옵션 창과 서버 응답 대기는 전경 상태이면 포함. 최근 2초 길이와 별개의 방문 누적 값 |

반복은 시간·공간 패턴의 후보이며, 정상 수량 증가나 재선택도 포함될 수 있습니다. 오류·사용자 불편·실패로 해석하거나 자동 지원 기준으로 쓰지 않습니다. `pointer_start`를 장바구니 저장 성공으로 취급하지 않습니다.

집계 구간 전체가 연속해서 전경 관측되지 않았으면 횟수는 `null`입니다. 대상·입력 종료·전경 정보가 없거나 보관 버퍼가 잘려 필요한 맥락이 없으면 해당 값은 미산출입니다. 관측한 입력이 없는 구간의 0과 구분합니다. 시계 역행·미래 시각 기록·잘못된 구간도 산출하지 않습니다. 새 로컬 세션은 이전 세션 입력을 읽지 않습니다.

집계 구간 직전의 선행 누름도 현재 구간의 누름과 반복 쌍이 될 수 있습니다. 같은 방문에서 반복 시간 기준 안에 있는 선행 누름의 `isPrimary`·대상·종료 등 필수 정보가 부족하면 `repeat_tap_count`는 0 대신 `null`로 둡니다.

개발 창에서 반복 시간·거리를 바꾸고 체류 정의를 비교할 수 있습니다. 설정을 비우면 해당 값은 미산출입니다. 별도 **파일럿 집계 내보내기**는 정책·시각 구간·세션 ID·측정 여부를 포함한 `touch-features-pilot.json`을 만듭니다. 기존 원시 **JSON 내보내기**는 `touch-log-draft.json`으로 유지합니다. 개발 창의 입력은 수집 대상에서 제외합니다.

```js
window.kioskTouchLogDraft.features();
window.kioskTouchLogDraft.features({ repeatMs: 500, repeatPx: 16, dwellMode: 'foreground_visit' });
```

### 주문 화면

- 기본 본문 28px를 기준으로 작은 문자들의 별도 축소를 없애고, 큰 글씨는 200%로 확대합니다. 색 대비를 조정하고 수동 고대비 설정을 추가합니다. `highContrast`는 로컬 설정·로그 복사본에만 포함하며 서버 프리셋에 추가하지 않습니다. 이전 저장 형식은 `false`로 복원합니다.
- 하단 주문 바 높이를 관측해 본문 여백과 개발 창 위치를 조절합니다. 짧은 창·낮은 화면·200% 확대에서는 영역별 스크롤로 내용과 버튼에 접근하며, 오류 안내도 가용 높이 안에서 스크롤할 수 있습니다.
- 처음으로 버튼은 확인 창에서 계속 주문·새 주문을 선택합니다. 확인하면 기존 상품 조회·세션 생성·장바구니 조회 API로 새 이용을 시작합니다. 진행 중·결과 불확실 요청은 초기화로 버리지 않으며 기존 재확인 절차를 따릅니다. 서버의 이전 세션 삭제·주문 취소를 뜻하지 않습니다.
- 상품 이모지와 장식 화살표를 정리하고 단계 번호·음성 입력 안내를 쉬운 문구로 바꿉니다. 기존 `data-log-target` ID는 유지합니다. 통합 확대 확인 버튼은 개발 모드에만 표시합니다.
- 화면 도움의 음성 안내는 브라우저 내장 TTS로 현재 화면 또는 열린 옵션·처음으로 확인 창을 읽으며 켜기·끄기·중단·다시 읽기를 제공합니다. 화면·세션 변경, 페이지 비활성화, 마이크 사용 시 이전 안내를 취소합니다. 마이크를 열기 전에 낭독·누름 소리를 멈추고, 화면 읽기로 전환할 때는 실제 마이크 종료 이벤트까지 기다립니다. 음성 입력의 인식문은 읽지 않습니다. 누름 소리는 사용자가 켤 때만 Web Audio로 재생하며 마이크 사용 중에는 멈춥니다. 음성 기능 설정은 새로고침 시 꺼집니다.
- 직원 호출은 연결 API·운영 연락처가 제공되지 않아 추가하지 않습니다. 이전 화면으로 돌아갈 때의 서버 입력 삭제 범위도 별도 합의 대상입니다. KoddiUD 글꼴 교체는 적용하지 않았습니다. 실제 문자 높이(mm), G10 터치 도달 범위·스피커·한국어 음성 설치 상태는 실물 검증이 필요합니다.

일반 테마의 배경·버튼색은 `orderAccessibility.css`의 `.kiosk`에 있는 `--ui-surface`, `--ui-canvas`, `--ui-accent`, `--ui-on-accent` 등으로 조정합니다. 고대비의 `.kiosk.high-contrast`는 별도 값을 가지므로 일반 팔레트 변경과 독립적으로 적용됩니다. 공통 버튼에 고정 색이나 인라인 `--ui-*` 값을 덮어쓰면 이 우선순위가 달라질 수 있습니다. 색을 변경한 뒤에는 일반/고대비의 문자 대비와 버튼 식별에 필요한 경계·선택 상태의 대비를 다시 검사합니다.
