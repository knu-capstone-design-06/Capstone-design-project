# 상품·서버 장바구니·모의 주문 API 검토 초안

- 작성일: 2026-10-04
- 수정일: 2026-10-10 — 프론트 담당 범위로 정리하고 백엔드 구현 대기 상태 반영.
- 상태: OpenAPI 0.3.0에 반영한 팀 검토용 초안. 아래 경로·필드·제한·상태 코드는 팀 합의 전 제안입니다.
- 기준 명세: `contract/frontend-backend.openapi.yaml` 0.3.0. 기존 0.1.0의 네 API 형식은 유지합니다.
- 대상: 프론트엔드·백엔드 담당자. 이번 작업에서 음성·MCP 연동은 제외합니다.

이 문서는 서버 장바구니 방식으로 상품 조회부터 모의 주문 확정까지 연결하기 위한 제안입니다. 2026-10-07 사용자 요청으로 상품·장바구니·모의 주문 API를 OpenAPI 0.2.0에 반영했으며, 신규 operation은 `x-contract-status: draft`로 표시합니다. 프론트 타입·호출 함수·화면 상태 처리는 이 초안에 맞춰 준비했으며 서버 연결 완료는 아닙니다. 2026-10-10 사용자 요청으로 이전에 추가했던 백엔드 구현·환경 설정과 공용 계약 변경을 제거했습니다. 서버 업무 로직은 백엔드 담당자가 구현하고 프론트는 응답을 표시합니다. 현재 기준 명세는 0.3.0이며, 후속 요청으로 프론트 준비·백엔드 대기 상태와 재시도 설명을 계약에 다시 반영했습니다. 팀 전체 합의는 별도 기록합니다.

## 1. 범위와 상태 관리

백엔드가 세션별 장바구니의 기준 상태를 관리합니다. 프론트는 서버가 반환한 장바구니를 표시하고, 상품 선택 창·로딩·오류·접근성 설정 같은 화면 상태를 관리합니다. 터치 변경은 백엔드 장바구니 서비스의 검증을 거치는 방향을 제안합니다. 프론트는 성공 응답 후 수량·금액을 확정 표시하며 서버 저장·검증 로직을 직접 구현하지 않습니다.

```text
이용 시작 → 상품 조회 → 세션 생성 → 장바구니 조회
터치 조작 → 장바구니 변경 API → 백엔드 검증·저장 → 최신 장바구니 표시
주문 확인 → 모의 주문 확정 → 서버 주문번호 표시
```

- 프론트가 보낸 가격이나 로컬 총액을 주문 금액의 기준으로 사용하지 않습니다.
- 상품 가격·판매 가능 여부·옵션·수량은 백엔드가 검증합니다.
- UI 지원을 바꿔도 서버 장바구니와 세션을 유지합니다.
- 첫 시연용 프론트는 새로고침 시 새 세션을 요청합니다. 접근성 설정만 로컬에 유지하고 이전 로컬 장바구니로 서버를 덮어쓰지 않습니다. 복원은 후순위입니다.
- 실제 결제·상품 관리자 화면·재고 차감·음성 API·WebSocket 형식은 이번 초안의 구현 범위에서 제외하며 관련 정책은 별도로 합의합니다.
- 기존 세션 생성 API·응답 필드를 그대로 사용합니다. 프론트가 별도 서버 세션 API나 저장소를 만들지 않습니다.
- 사용자가 선택한 ‘한 세션 1주문·새 주문은 새 세션’ 방향에 따라 완료 화면에서 새 세션을 요청합니다. 서버의 완료 세션 제어는 백엔드 담당자의 구현·팀 합의가 필요합니다.

| 구분 | 상태 |
|---|---|
| 프론트 구현 | 상품·장바구니·주문 타입/호출 함수, 성공 응답 후 표시, 대기·오류·수동 재시도, 충돌 응답 표시 |
| 최신 원격 main | `ff79f1a` / PR #26에서 상태·연결 확인·임시 세션·특징 전송 구현. 상품·장바구니·주문은 미구현 |
| 백엔드 담당 작업 | 상품 데이터·가격·옵션 검증, 서버 장바구니·합계·버전, 모의 주문번호·중복 방지, 접근 정책 |
| 후순위 | 새로고침·완료 화면 복원, 재시작 후 유지, 24시간 보관, 유휴 만료·안내, 동적 가격 변경 |
| 제외 | 음성·MCP·SSE, 실제 결제·재고 차감·관리자 화면 |

최신 main ff79f1a는 처음에 읽어서 확인했고, 이후 사용자 요청으로 feat/frontend에 병합했습니다. 백엔드 담당자의 코드를 반영했으며 프론트 작업에서 백엔드 Python 코드·환경 설정·Docker 설정을 별도로 수정하지 않습니다. 후속 사용자 요청으로 OpenAPI에는 프론트 준비·백엔드 구현 대기 상태와 동작 설명·선택적인 Retry-After 제안을 반영했으며 팀 검토 초안 상태를 유지합니다. 백엔드 경로에서는 Markdown 문서만 변경합니다.

## 2. 엔드포인트 제안

| 메서드 | 경로 | 목적 | 정상 응답 |
|---|---|---|---|
| POST | `/api/v1/sessions` | 이용 세션 생성 — 기존 계약 유지 | 201 |
| GET | `/api/v1/products` | 상품·선택 가능한 온도·판매 가능 여부 조회 | 200 |
| GET | `/api/v1/sessions/{session_id}/cart` | 세션 장바구니 조회 | 200 |
| POST | `/api/v1/sessions/{session_id}/cart/items` | 상품 추가, 같은 옵션이면 수량 합산 | 200 |
| PATCH | `/api/v1/sessions/{session_id}/cart/items/{item_id}` | 항목 수량을 지정 값으로 변경 | 200 |
| DELETE | `/api/v1/sessions/{session_id}/cart/items/{item_id}` | 항목 삭제 | 200 |
| POST | `/api/v1/sessions/{session_id}/orders` | 장바구니를 모의 주문으로 확정 | 201 |

상품은 모두 조회한 뒤 프론트에서 분류합니다. 현재 규모에서는 페이지네이션·검색 API를 필수로 두지 않습니다. 기존 `POST /api/v1/sessions` 응답을 그대로 사용합니다. 빈 장바구니도 생성된 세션에 대해 200으로 반환합니다.

신규 장바구니·주문 변경 API는 성공 시 결과 상태를 반환합니다. DELETE도 변경된 장바구니를 반환하므로 204 대신 200을 제안합니다. 주문 단건 조회가 필요한지는 재접속·주문 완료 화면 복원 요구에 따라 추가 합의합니다.

### 기존 세션 생성 명세

```http
POST /api/v1/sessions
```

요청 본문은 없습니다. 기존 계약의 응답 필드를 유지하며, 장바구니는 별도로 조회합니다.

```json
{
  "session_id": "session-1",
  "started_at": "2026-10-07T05:00:00Z"
}
```

`session_id`는 필수 문자열, `started_at`은 필수 RFC 3339 시각입니다. 기존 계약에 정의된 경로라는 뜻이며, 이 문서가 서버 구현 완료를 의미하지는 않습니다. 최신 원격 main에는 이 성공 형식을 사용하는 임시 세션 생성이 구현돼 있습니다. 만료·접근·주문 완료 후 재사용 제어는 백엔드와 합의할 항목입니다.

### 요청·응답 공통 규칙

- 본문이 있는 요청과 응답은 `application/json`을 사용합니다. GET·DELETE와 세션 생성 요청에는 JSON 본문을 넣지 않습니다.
- API 필드명은 `snake_case`를 사용합니다.
- `/api/v1`은 백엔드 경로입니다. 프론트의 개발·Docker 프록시를 사용할 때는 `/backend/api/v1/...`로 요청하며 `/backend`는 프록시에서 제거합니다.

## 3. 공통 표현

| 항목 | 제안 |
|---|---|
| ID | 서버가 관리하는 비어 있지 않은 문자열. 프론트가 형식에 의존하지 않음 |
| 가격 | 원 단위의 0 이상 정수. 통화는 `KRW` |
| 시각 | 시간대가 포함된 RFC 3339 문자열, 서버는 UTC `Z`로 반환 |
| 버전 | 세션 장바구니별 0 이상 정수. 변경 성공마다 1 증가 |
| 수량 | 항목별 1~20 정수. 0은 삭제 의미로 사용하지 않음 |
| 온도 | `iced`, `hot`; 선택 없는 푸드는 `null` |
| 필수·결측 | 별도로 선택이라고 표시한 필드 외에는 필수. 온도 없음은 생략 대신 `null` |

20개 제한은 현재 시제품에 맞춘 제안입니다. 최종 제한, 주문당 항목 수·전체 수량 제한은 팀이 확정합니다. 온도 이외 크기·샷·우유 옵션은 요구사항 확정 후 확장합니다.

## 4. 상품 조회

응답은 `products` 배열과 `currency`를 포함합니다. 응답 본문의 필드는 다음과 같습니다.

| 필드 | 타입 | 의미 |
|---|---|---|
| `currency` | string | `KRW` |
| `products` | Product[] | 상품 목록. 상품이 없으면 `[]` |

Product의 필드는 다음과 같습니다.

| 필드 | 타입 | 의미 |
|---|---|---|
| `product_id` | string | 서버 상품 ID |
| `name` | string | 화면 표시명 |
| `category` | string | `coffee`, `drink`, `food` 제안 |
| `description` | string | 설명. 없으면 빈 문자열 |
| `unit_price` | integer | 현재 단가, 원 |
| `available` | boolean | 주문 가능 여부. 구체적인 재고 수량을 의미하지 않음 |
| `temperatures` | string[] | 허용 온도 목록. 푸드는 빈 배열 |

```json
{
  "currency": "KRW",
  "products": [
    { "product_id": "americano", "name": "아메리카노", "category": "coffee", "description": "깊고 깔끔한 에스프레소", "unit_price": 3500, "available": true, "temperatures": ["iced", "hot"] },
    { "product_id": "sandwich", "name": "에그 샌드위치", "category": "food", "description": "든든한 달걀 샌드위치", "unit_price": 5500, "available": true, "temperatures": [] }
  ]
}
```

이미지 URL은 저장 위치가 결정되지 않아 필수 필드로 제안하지 않습니다. 프론트의 현재 이모지는 표시용 샘플이며 주문 정보가 아닙니다. 실제 상품 ID·데이터 공급 및 변경 방법은 백엔드 담당자가 합의 후 구현합니다.

## 5. 장바구니 조회·변경 응답

모든 장바구니 응답의 필드는 필수입니다.

| 필드 | 타입 | 의미 |
|---|---|---|
| `session_id` | string | 장바구니 소유 세션 |
| `version` | integer | 동시 변경 감지용 버전 |
| `currency` | string | `KRW` |
| `items` | CartItem[] | 장바구니 항목. 비어 있으면 `[]` |
| `total_quantity` | integer | 모든 항목 수량 합 |
| `total_amount` | integer | 모든 항목 금액 합, 원 |
| `updated_at` | date-time | 서버 상태 갱신 시각 |

CartItem은 `item_id`, `product_id`, `name`, `temperature`, `quantity`, `unit_price`, `line_amount`를 포함합니다. `item_id`는 상품·옵션 조합에 대응하는 서버 항목 ID이고 `line_amount = unit_price × quantity`입니다. 푸드의 `temperature`는 `null`입니다.

| CartItem 필드 | 타입 | 의미 |
|---|---|---|
| `item_id` | string | 장바구니 항목 ID. 상품 ID와 구분 |
| `product_id` | string | 상품 ID |
| `name` | string | 상품 표시명 |
| `temperature` | `iced` · `hot` · null | 선택한 온도 |
| `quantity` | integer | 항목 수량. 1~20 제안 |
| `unit_price` | integer | 적용 단가, 원 |
| `line_amount` | integer | 단가 × 수량, 원 |

초기 빈 장바구니의 `version`은 0으로 제안합니다. 첫 시연용 프론트는 새로고침 시 새 세션과 빈 장바구니를 요청하며, 이전 로컬 장바구니는 사용하지 않습니다.

```json
{
  "session_id": "session-1",
  "version": 2,
  "currency": "KRW",
  "items": [
    { "item_id": "item-1", "product_id": "americano", "name": "아메리카노", "temperature": "iced", "quantity": 2, "unit_price": 3500, "line_amount": 7000 },
    { "item_id": "item-2", "product_id": "sandwich", "name": "에그 샌드위치", "temperature": null, "quantity": 1, "unit_price": 5500, "line_amount": 5500 }
  ],
  "total_quantity": 3,
  "total_amount": 12500,
  "updated_at": "2026-10-04T10:00:00Z"
}
```

첫 시연은 고정 상품·가격으로 시작하는 방향을 제안합니다. 상품 데이터는 백엔드가 제공합니다. 동적 가격 변경을 도입한다면 사용자는 주문을 만들지 않고 전체 가격·금액을 갱신하고 버전을 올린 뒤 재확인하는 방향을 선택했으며, 팀 합의·구현은 후순위입니다.

## 6. 상품 추가·변경·삭제

### 추가 요청

```http
POST /api/v1/sessions/session-1/cart/items
Idempotency-Key: <사용자 동작마다 생성한 UUID>
Content-Type: application/json
```

```json
{ "product_id": "americano", "temperature": "iced", "quantity": 2, "expected_version": 0 }
```

`product_id`는 문자열, `temperature`는 허용 온도 또는 null, `quantity`는 1~20 정수, `expected_version`은 0 이상 정수입니다. 성공 시 갱신된 전체 Cart를 반환합니다.

- 모든 필드는 필수입니다. 온도 선택이 없는 상품은 `temperature: null`로 보냅니다.
- 같은 상품·온도 항목이 있으면 수량을 합산하고, 없으면 항목을 만듭니다.
- 합산해서 20개를 넘으면 임의로 잘라내지 않고 409 `quantity_limit_exceeded`로 변경 전체를 거절합니다.
- 허용되지 않은 온도 또는 푸드에 온도를 지정하는 요청은 422 `invalid_option` 제안입니다. 필수 `temperature` 누락 등 요청 형식 오류는 422 `invalid_request`로 구분합니다.

### 수량 변경 요청

```http
PATCH /api/v1/sessions/session-1/cart/items/item-1
Idempotency-Key: <UUID>
Content-Type: application/json
```

```json
{ "quantity": 3, "expected_version": 2 }
```

수량은 추가할 개수가 아니라 변경 후의 절대값입니다. 대상은 경로의 `item_id`로 지정합니다.

`quantity`와 `expected_version`은 모두 필수 정수이며, 성공 시 갱신된 전체 Cart를 반환합니다.

### 삭제

DELETE에는 JSON 본문을 넣지 않고 필수 쿼리 `expected_version`을 사용합니다.

```text
DELETE /api/v1/sessions/session-1/cart/items/item-2?expected_version=2
Idempotency-Key: <UUID>
```

`expected_version`은 필수 0 이상 정수입니다. 성공 시 삭제 후 전체 Cart를 반환합니다.

상품·옵션 변경은 일단 기존 항목 삭제 후 새 항목 추가로 처리합니다. 단일 요청의 옵션 변경 기능이 필요하면 별도 합의합니다.

## 7. 동시 변경·재시도

반복 입력·외부 변경·응답 유실에 대비하도록 백엔드는 버전 확인·변경·결과 기록을 함께 처리하는 방향을 합의해야 합니다. 프론트는 서버가 보낸 버전과 결과만 사용합니다.

1. 프론트는 변경 시 마지막으로 받은 `version`을 `expected_version`으로 보냅니다.
2. 서버 버전과 다르면 409 `cart_version_conflict`와 최신 장바구니를 반환합니다.
3. 프론트는 최신 상태를 표시하고 사용자가 다시 확인하게 합니다. 특히 절대 수량 변경을 무조건 자동 재시도하지 않습니다.
4. 프론트는 같은 화면에서 처리 중인 변경 버튼을 잠시 막고, 오래된 버전의 응답으로 최신 장바구니를 덮어쓰지 않습니다.

신규 장바구니·주문 변경 API에 필수 `Idempotency-Key` 헤더를 제안합니다. 기존 세션 생성·특징 전송에는 이 헤더를 새로 요구하지 않습니다. 프론트는 사용자 동작마다 UUID를 생성하고, 응답을 못 받아 동일 요청을 재시도할 때만 같은 키를 씁니다.

- 서버는 세션·키에 대해 경로·메서드·쿼리·요청 본문을 함께 비교합니다. DELETE의 `expected_version`도 비교 대상입니다.
- 이미 성공한 같은 요청은 버전 검증 전에 원래 성공 응답을 반환하여 이중 추가·이중 주문을 막습니다.
- 같은 키에 다른 내용이면 409 `idempotency_key_reused`입니다.
- 성공 결과와 키 저장도 변경 처리와 함께 원자적으로 수행합니다. 키 보관 기간·실패 응답 재사용 정책은 미결정입니다.

사용자는 처리 중 오류와 재시도 간격을 반환하고 같은 키로 확인하는 방향을 선택했습니다. 구체적인 상태 코드·오류 코드·Retry-After 지원은 백엔드와 합의해야 합니다. 프론트는 409 응답에 Retry-After가 있을 때 같은 요청을 유지하고 수동 재시도 간격을 지킵니다. 처리 중인 중복 요청을 독립적인 새 변경으로 실행하지 않는 것이 제안의 전제입니다. 응답 유실로 재시도할 때는 기존 요청의 키·버전·본문을 유지하며, 버전 충돌 후 사용자가 최신 상태를 확인하고 다시 실행하는 동작에는 새 키를 사용합니다.

키 보관 기간·실패 응답 보관·처리 중 오류 코드·원자적 저장 구현은 백엔드 담당 범위입니다. 프론트가 해당 서버 정책을 대신 구현하거나 미합의 오류 코드를 계약에 추가하지 않습니다. 음성 연결은 이번 작업에서 제외합니다.

## 8. 모의 주문 확정

```http
POST /api/v1/sessions/session-1/orders
Idempotency-Key: <UUID>
Content-Type: application/json
```

```json
{ "expected_version": 2 }
```

세션 ID는 경로, 중복 방지 키는 헤더에 넣습니다. 상품·가격·수량을 요청에 다시 넣지 않고 서버 장바구니를 기준으로 확정합니다.

```json
{
  "order_id": "order-1",
  "order_number": "A001",
  "session_id": "session-1",
  "status": "simulated",
  "currency": "KRW",
  "items": [
    { "item_id": "item-1", "product_id": "americano", "name": "아메리카노", "temperature": "iced", "quantity": 2, "unit_price": 3500, "line_amount": 7000 },
    { "item_id": "item-2", "product_id": "sandwich", "name": "에그 샌드위치", "temperature": null, "quantity": 1, "unit_price": 5500, "line_amount": 5500 }
  ],
  "total_quantity": 3,
  "total_amount": 12500,
  "created_at": "2026-10-04T10:01:00Z"
}
```

모든 응답 필드는 필수입니다. 주문 항목·금액은 확정 시점의 스냅샷으로 저장하고 이후 상품 변경으로 바꾸지 않습니다. 주문번호의 형식·유일성 범위는 백엔드 담당자와 확정합니다.

| Order 필드 | 타입 | 의미 |
|---|---|---|
| `order_id` | string | 서버 주문 ID |
| `order_number` | string | 사용자에게 표시할 주문번호 |
| `session_id` | string | 주문한 세션 |
| `status` | string | 이번 범위에서는 `simulated` |
| `currency` | string | `KRW` |
| `items` | CartItem[] | 확정 시점의 항목 스냅샷 |
| `total_quantity` | integer | 확정 수량 합 |
| `total_amount` | integer | 확정 금액 합, 원 |
| `created_at` | date-time | 주문 생성 시각 |

`simulated`는 실제 결제가 발생하지 않았음을 뜻합니다. 결제 승인이나 실제 주문 처리 상태로 해석하지 않습니다.

확정과 장바구니 비우기를 원자적으로 처리하고 버전을 증가시키는 방식을 제안합니다. 빈 장바구니·가격 변경·품절·버전 충돌이면 주문을 만들지 않습니다. 재시도 시 같은 주문 결과를 반환하고, 주문 성공 전 프론트가 임의로 장바구니를 비우지 않습니다. 세션을 즉시 종료할지 여부는 합의가 필요합니다.

주문 실패 시 장바구니 항목을 임의로 삭제하거나 비우지 않습니다. 가격 변경에 따른 최신 장바구니 반환 시 단가 갱신 범위와 버전 증가 정책은 별도로 합의합니다.

## 9. 오류 형식 제안

기존 네 API의 오류 형식은 변경하지 않습니다. 신규 API에는 구분 가능한 `code`를 사용하며, OpenAPI 0.3.0의 `OrderApiError` 스키마로 정의합니다.

```json
{
  "code": "invalid_option",
  "detail": "이 상품에서 선택할 수 없는 온도입니다.",
  "cart": null
}
```

- `code`: 필수 문자열, 프론트 분기용 오류 코드.
- `detail`: 필수 문자열, 오류 설명.
- `cart`: 필수 `Cart | null`. 409 버전·가격 충돌에는 최신 장바구니, 복원할 상태가 없으면 `null`.

| 상태 | 코드 제안 | 상황 |
|---|---|---|
| 404 | `session_not_found`, `product_not_found`, `cart_item_not_found` | 대상 없음 |
| 410 | `session_expired` | 세션 만료, 유지 데이터·복구 정책 합의 필요 |
| 409 | `cart_version_conflict` | 터치·음성 등으로 버전 변경 |
| 409 | `product_unavailable`, `price_changed` | 품절·가격 변경으로 재확인 필요 |
| 409 | `quantity_limit_exceeded`, `empty_cart` | 합산 한도 초과·빈 주문 |
| 409 | `idempotency_key_reused` | 같은 키에 다른 요청 |
| 422 | `invalid_request`, `invalid_option` | 필수 필드·타입·수량·옵션 오류 |
| 503 | `service_unavailable` | 일시적인 서비스 불가 |

서버는 스키마 검증 오류도 신규 API에서 이 형식으로 맞춰야 합니다. 내부 예외·DB 접속정보는 응답하지 않습니다. 네트워크 단절·응답 유실은 HTTP 오류와 구분하여 프론트가 처리합니다. 실제 인증·인가 및 세션 ID의 안전한 사용 정책은 배포 환경에 맞춰 별도 합의합니다.

## 12. 프론트 검증과 실제 연동 구분

프론트 단위 테스트는 준비된 응답을 주입하고, 브라우저 테스트는 HTTP 응답을 가로채 고정된 응답을 전달합니다. 테스트 응답은 실제 앱에서 사용하지 않으며 서버 구현·인증·중복 방지 성공을 증명하지 않습니다.

- API 필드·경로·메서드·DELETE 쿼리·Idempotency-Key가 초안과 일치
- 상품 분류·iced/hot·푸드 null 대응
- 응답 전 수량·금액 유지와 처리 중 변경 차단
- 충돌 응답의 최신 Cart 표시, 재조작에 최신 버전·새 키 사용
- 응답 유실 후 동일 키·버전·본문으로 수동 재시도
- 서버 응답의 주문번호를 형식 가정 없이 표시하고 새 이용 요청
- 새 이용 시작 실패 후 재연결, 주문 API 미구현 시 연결 대기
- 새로고침 시 새 세션 요청과 접근성 설정 유지
- 1080×1920 기본·큰 글씨·큰 버튼 및 옵션·확인·완료 배치

백엔드 구현 후에는 실제 수량 합산·품절 검증·원자적 버전 처리·중복 주문 방지·세션 접근을 별도로 통합 검증합니다. 서버 없이 통과한 프론트 테스트를 실제 API 연동 완료로 기록하지 않습니다.
