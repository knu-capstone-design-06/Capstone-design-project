# 협업 규칙

## 1. 작업 관리

- 역할 라벨은 `frontend`, `backend`, `vision`, `ai`, `docs`를 사용합니다.
- 막힌 작업은 원인과 필요한 도움을 팀에 공유합니다.

## 2. 브랜치

작업 브랜치에서 `main`으로 PR을 올립니다.

- `main`: 시연 가능한 안정 버전
- 작업 브랜치: 아래 이름의 역할 브랜치와 공용 브랜치만 씁니다. 작업마다 다른 이름의 브랜치를 만들지 않습니다.
- 작업을 시작하기 전에 `main`의 최신 내용을 작업 브랜치로 가져옵니다(merge).
- `main`에 직접 push하지 않고 PR로 병합합니다.
- 다른 사람이 작업 중인 브랜치(열린 PR의 브랜치, 공용 브랜치 포함)에는 커밋을 올리지 않습니다. git push뿐 아니라 GitHub 웹의 제안 적용(`Commit suggestion`), 충돌 해결, `Update branch`, 파일 편집도 커밋을 올리는 일입니다. 고칠 점은 PR 리뷰(변경 요청, 코드 제안)로 남기고 PR 작성자가 반영합니다.
- 예외: 리뷰어가 직접 반영해야 할 때는 그 PR에서 작성자와 수정할 사람을 먼저 합의합니다. 커밋을 올린 사람은 같은 PR에 커밋과 변경 내용을 바로 적습니다.
- `test`: 각 팀원이 만든 코드를 합쳐 서버 연결을 확인하는 임시 브랜치입니다. 확인이 끝나면 지웁니다.

브랜치 이름:
- 역할 브랜치: `feat/frontend`, `feat/backend`, `feat/vision`, `feat/ai` — 담당자가 계속 사용합니다.
- 공용 브랜치: `feat/infra`(배포·실행 설정), `feat/db`(DB), `feat/docs`(문서) — 역할 영역 밖의 변경이 있을 때 이 이름으로 만들어 쓰고, 쓰지 않으면 지웁니다.

## 3. 커밋

형식: `타입: 변경 내용`

- `feat`: 기능 추가
- `fix`: 오류 수정
- `refactor`: 기능 변경 없는 코드 개선
- `docs`: 문서 수정
- `test`: 테스트 추가·수정
- `chore`: 설정·의존성 등 기타 작업

예시: `feat: 음성 글자 확대 명령 추가`

관련 없는 변경은 별도 커밋으로 나눕니다.

## 4. Pull Request

- 하나의 PR은 하나의 작업 목적에 집중합니다.
- 작업 브랜치에서 `main`으로 PR을 생성합니다.
- PR 본문에 변경 내용과 확인 방법을 작성합니다.
- UI 변경은 스크린샷, API 변경은 요청·응답 예시를 첨부합니다.
- 작성자 외 팀원 1명 이상의 승인 후 병합합니다.
- 병합은 PR 작성자가 합니다. 다른 사람이 대신 병합하려면 작성자가 그 PR에 "다른 사람이 병합해도 됩니다"라고 적은 뒤에 합니다. 미리 적어 두어도 됩니다.
- 병합하는 사람은 병합 전에 같은 파일을 고치는 다른 열린 PR이 있는지 살핍니다. 있으면 두 PR의 작성자들이 병합 순서를 정하고, 뒤에 병합하는 PR의 작성자가 앞선 병합 결과를 자기 브랜치에 merge해 충돌과 어긋난 내용을 고칩니다. 작성자가 답하지 않으면 병합을 미루고 팀 채널에 알립니다.
- 승인 뒤에 커밋이 더 올라오면 리뷰어는 마지막 커밋을 다시 검토해 승인합니다. 병합하는 사람은 마지막 커밋에 승인이 있는지 살핀 뒤 병합합니다.
- 병합 후 Project 상태를 갱신합니다. 역할 브랜치는 삭제하지 않습니다.

## 5. 담당 영역과 인터페이스

- 다른 담당자의 영역을 수정할 때는 먼저 PR에서 공유합니다.
- API·터치 로그·비전 결과·AI 명령 형식은 `contract/`에서 관리합니다.
- 인터페이스 변경은 영향받는 담당자와 합의한 뒤 구현합니다.
- 필드 이름, 단위, 필수 여부, 결측값, 오류 형식을 명시합니다.
- 실제 모듈이 준비되지 않았으면 합의된 샘플 데이터로 연결합니다.

## 6. 코드와 데이터

- PR 전 변경과 관련된 빌드·테스트·수동 확인을 수행합니다.
- API 키, 비밀번호, `.env`, 개인 식별 정보는 커밋하지 않습니다.
- 환경변수 항목은 값 없이 `.env.example`에 기록합니다.
- 원본 영상, 대용량 데이터셋, 모델 가중치는 Git에 직접 올리지 않습니다.
- 데이터·모델의 저장 위치, 버전, 사용 방법을 문서화합니다.

## 7. 실험과 기록

- 실험에 사용한 UI·비전 모델·Jev 지침·규칙 버전을 기록합니다.
- 미검출, 측정 불가, 시스템 오류를 구분합니다.
- 파일럿 데이터와 최종 평가 데이터를 분리합니다.
- 최종 평가 중 조건을 변경하면 변경 이유와 적용 시점을 남깁니다.
- 회의에서 결정한 변경 사항은 관련 문서에 반영합니다.
