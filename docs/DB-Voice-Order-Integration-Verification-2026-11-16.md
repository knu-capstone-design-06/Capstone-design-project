# DB 모드 음성 주문 통합 검증 — 2026-11-16

실제 마이크 입력부터 OpenAI 해석, 서버 장바구니 변경, 모의 주문 완료와 Supabase 저장까지 한 시나리오를 연결해 확인했다. 백엔드 프로세스를 재시작한 뒤 같은 주문을 재전송해도 주문이 한 건만 유지됐다. 이 문서는 실행 결과 기록이며 계약이나 서비스 동작을 변경하지 않는다.

## 1. 검증 기준과 환경

- 검증 소스: `94152430ac8978453796dfc6a375e8db156089b0`의 백엔드·프론트엔드. 문서 작성 시점 main `b859e67a2a1d7f6e56b640944af390049fdbc256`과 두 영역의 내용이 같음을 확인했다.
- 프론트엔드: 기존 Dockerfile로 만든 프로덕션 빌드. 개발용 샘플 어댑터 대신 `/backend/` 프록시로 실제 백엔드를 호출했다. 프론트 파일은 수정하지 않았다.
- 백엔드: 기존 FastAPI 앱을 호스트에서 실행. 프론트 프록시만 해당 임시 서버를 바라보도록 설정했다. 전체 Compose 배포를 검증한 것은 아니다.
- 저장: `DATABASE_URL`로 설정된 시연용 Supabase의 `kiosk_backend` 역할과 TLS 연결. 세션·Cart·주문·주문 API 성공 응답 재생 기록은 DB 모드였다. 음성 요청·대화 이력은 기존대로 메모리에 남는다.
- 실제 음성 해석: `OPENAI_MODEL=gpt-4o-mini`, 프롬프트 `interpret_v3`, `VOICE_EXECUTE_TOOLS=true`, 호출 제한 20초. 이 설정은 검증 프로세스에만 적용했고 제품의 기본값은 바꾸지 않았다.
- Jev 키는 설정하지 않았고 비전·자동 접근성 지원 경로는 호출하지 않았다.
- 자동 브라우저 검사는 Edge headless의 1080×1920 환경에서 실행했다. 실제 마이크 검사는 개발 PC의 사용자 조작으로 진행했으며 브라우저 버전·배율은 별도로 기록하지 않았다. 이 기록의 검증 범위는 Edge headless와 개발 PC이며, 시험 기기 검증은 후속 과제다.
- 로컬 DB 검사에는 Docker Engine 29.6.2와 일회용 PostgreSQL 17을 사용했다. 원격 Supabase의 스키마·시드를 다시 적용하지 않았다.

## 2. 실제 마이크·OpenAI·Supabase 결과

검증 발화는 **“아이스 아메리카노 한 잔 담아줘”**였다. 음성을 통해 결제를 실행하지 않았으며, 장바구니 반영 뒤 사용자가 화면의 주문 확인·모의 주문 버튼을 눌렀다.

| 확인 항목 | 결과와 근거 |
|---|---|
| 실제 마이크 입력 | 사용자가 마이크로 입력하고 아메리카노가 담긴 화면을 확인했다고 답했다 |
| 실제 OpenAI 해석 | HTTP 200 응답 1회, 음성 상태 `completed` |
| 장바구니 실행 | 음성 상태 응답의 `actions: ["cart_updated"]` 확인 |
| 상품·옵션·수량 | 아메리카노(`americano`)·아이스(`iced`)·1개 |
| 금액·주문 종류 | 3,500원, `status: simulated`. 실제 결제·재고 차감 없음 |
| 주문번호 표시 | 사용자가 완료 화면의 `SIM-` 주문번호까지 확인했다고 답했다 |
| DB 저장 | 백엔드 전용 역할의 직접 조회와 별도의 Supabase 조회로 주문·주문 항목을 대조했다 |
| 프로세스 재시작 | 기존 백엔드 프로세스를 종료하고 새 프로세스로 실행했다 |
| 주문 성공 응답 재생 | 같은 `Idempotency-Key`·같은 본문을 재전송해 최초 응답과 완전히 같은 201 응답을 확인했다 |
| 중복 주문 방지 | 해당 합성 세션의 주문 수가 재시작·재전송 후에도 1건이었다 |
| 완료 세션 경계 | Cart 조회와 새 음성 요청이 각각 410으로 거절됐다 |
| 추가 AI 호출 방지 | 재시작 후 재전송·완료 세션 검사 중 OpenAI 호출 수가 늘지 않았다 |

최초 시도에서는 잘못 입력된 키에 OpenAI가 401을 반환해 음성 요청이 실패했다. 전체 키를 다시 입력한 후 위 시나리오가 성공했다. 인증 실패 시도와 성공 시도는 서로 다른 합성 세션이며, 실패 세션에는 주문이 없었다. 인증 실패를 음성 해석 정확도나 DB 저장 오류로 집계하지 않는다.

## 3. 고정 응답 자동 검사와의 구분

실제 마이크 검사 전에 브라우저 음성 인식 객체와 OpenAI 응답만 고정값으로 대체한 자동 검사도 수행했다. 프론트·백엔드 HTTP와 DB 저장은 실제 구현을 사용했다.

| 자동 검사 | 일회용 로컬 PostgreSQL | 원격 Supabase |
|---|---|---|
| 인식 문장 → 장바구니 재조회·아이스 아메리카노 1개 표시 | 통과 | 통과 |
| 화면 주문 확인 → 모의 주문 완료·주문번호 표시 | 통과 | 통과 |
| DB 주문·항목 직접 대조 | 통과 | 통과 |
| 실제 프로세스 재시작 후 동일 주문 응답 재생·주문 1건 유지 | 통과 | 통과 |
| 완료 세션 Cart 조회·새 음성 요청 410 | 통과 | 통과 |

자동 검사에서 API 과금은 없었고, 2절의 실제 OpenAI 검사에는 과금 가능한 요청이 있었다. 가상 인식 성공을 실제 마이크 검증으로 세거나, 이전 메모리 모드의 결과를 이번 DB 모드 결과로 대신하지 않았다.

## 4. 기존 회귀 검사 8개

저장소의 마이그레이션 3개와 상품 17개 시드로 준비한 일회용 로컬 PostgreSQL에서 다음 명령을 실행해 **8개 모두 통과**했다. `TEST_DATABASE_URL`은 준비된 로컬 임시 DB를 가리켰다.

```powershell
# backend/에서 실행. TEST_ADMIN_URL·TEST_DATABASE_URL은 로컬 임시 DB 전용.
python tests/setup_postgres_ci.py
python -m unittest tests.test_postgres_ordering tests.test_voice_order_flow -v
```

- `tests.test_postgres_ordering`: 애플리케이션/저장소 재생성 후 성공 응답 재생, 완료 세션 경계, 동일 버전 동시 Cart 변경, 음성 도구 묶음 롤백, 같은 키의 다른 본문 거절, 서로 다른 저장소의 동시 주문 등 7개.
- `tests.test_voice_order_flow`: 고정 OpenAI 응답으로 음성→Cart 변경→같은 음성 요청 재전송 중복 방지→모의 주문 1개. 이 검사는 메모리 저장소를 사용하며, 원격 DB나 실제 모델을 호출하지 않는다.

경쟁·롤백 검사는 로컬 임시 DB에서 수행했다. 이번에 원격 Supabase에 동시 부하나 장애를 주입한 것은 아니다. 준비 스크립트는 새 일회용 DB에만 적용하고 이미 적용한 원격 마이그레이션을 재실행하지 않는다.

## 5. DB 확인과 데이터 정리

- 적용 이력은 `20261007072436`, `20261012110139`, `20261101092640` 3건이며 판매 가능 상품은 17개였다.
- `kiosk`의 7개 테이블 모두 RLS가 켜져 있었고, `anon`·`authenticated` 역할에는 스키마 USAGE 권한이 없음을 읽기 조회로 확인했다. 이것이 공개 접속자의 세션 소유권 검증을 대신하지는 않는다.
- 이번 실행의 합성 세션·주문만 식별자로 대조한 뒤 관리자 작업으로 정리했다. 실제 주문의 상품·금액·수량과 인증 실패 세션의 주문 0건을 먼저 확인했다.
- 정리 후 실제 마이크 성공·인증 실패 세션의 session·cart·order·replay는 모두 0건이었다. 앞선 고정 응답 원격 검사 데이터도 정리했다. 기존의 다른 데이터와 DB 스키마는 변경하지 않았다.
- 관리자 삭제는 검증 데이터 정리 목적이다. 제품의 `kiosk_backend` 역할에 세션·주문 삭제 권한을 추가하지 않았다.

## 6. 재확인 절차와 근거 보관 범위

팀원이 다시 확인할 때의 순서는 다음과 같다.

1. 검증할 커밋·모델·프롬프트·브라우저·설정을 기록하고, 고정 응답 검사와 실제 호출 검사를 구분한다.
2. 시연 DB의 기존 마이그레이션·17개 상품과 전용 역할 접속을 확인한다. 키와 DB URL은 서버 환경에만 넣는다.
3. `DATABASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL=gpt-4o-mini`, `VOICE_EXECUTE_TOOLS=true`를 설정한 백엔드와 그 서버를 바라보는 프론트 프록시를 실행한다.
4. 새 테스트 세션에서 마이크로 위 문장을 입력하고 상품·옵션·수량을 확인한 뒤 화면으로 모의 주문을 완료한다.
5. DB의 주문·항목을 대조하고, 주문의 요청 키·본문·성공 응답을 검증용으로 별도 보관한다. 백엔드를 완전히 재시작한 뒤 같은 요청의 응답·주문 수와 완료 세션 410을 확인한다.
6. 이번 실행의 합성 데이터만 정리하고 잔존 건수와 검사 결과를 기록한다. 운영·참가자 데이터에는 이 절차를 적용하지 않는다.

이번 실행은 저장소 밖의 임시 검증 래퍼로 프로세스 재시작과 응답 대조를 자동화했다. 래퍼는 제품의 실제 OpenAI 전송·해석·DB 코드를 사용하며, 키는 터미널의 숨김 입력으로 받았다. 임시 래퍼와 원시 결과 JSON은 이 문서 PR에 포함하지 않는다. 따라서 위 절차는 팀 재확인 순서이며, 새 clone에서 이번 수동 검증 전체를 한 명령으로 재실행하는 도구를 추가한 것은 아니다.

개발 PC의 저장소 밖에 보관한 근거 파일은 `db_mode_demo_local_20261116.json`, `db_mode_demo_supabase_20261116.json`, `db_real_microphone_20261116-144317.json` 및 자동 브라우저 완료 화면 PNG다. 실제 마이크 완료 화면은 사용자 확인으로 기록했으며 자동 검사 PNG를 그 증거로 대신하지 않는다. API 키·DB URL·세션 ID·주문 요청 키를 이 문서에 복사하지 않았다.
