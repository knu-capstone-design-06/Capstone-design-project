# 첫 시연 상품·모의 주문·세션 정책 합의안

상태: **첫 시연 정책 A·B·C 채택 — 전체 주문 API 계약은 검토 중** (2026-10-15)

이 문서는 첫 시연의 주문 범위를 기록한다. 2026-10-15 백엔드 담당자의 명시적 요청으로 아래 A·B·C를 현재 제안대로 채택했다. 이는 PR #46의 승인·병합을 팀 전체의 정책 합의로 해석한 결과가 아니다. 프론트엔드 등 영향받는 담당자는 이 변경 PR에서 시연 화면과 계약의 일치 여부를 검토한다. [프론트↔백엔드 OpenAPI](../contract/frontend-backend.openapi.yaml)의 나머지 미정 사항이 남아 있으므로 `x-contract-status: draft`는 유지한다.

## 현재 구현과 결정

[PR #40](https://github.com/knu-capstone-design-06/Capstone-design-project/pull/40)의 백엔드는 [고정 카탈로그](../backend/app/modules/ordering/catalog.py)를 서버에서 제공하고, 장바구니의 옵션·수량·금액을 검증한다. 주문 확정은 실제 결제·재고 차감 없이 `simulated` 상태의 주문 스냅샷을 만든다. 한 세션의 주문 확정은 한 번만 허용하고, 완료된 세션의 장바구니 조회와 새로운 변경 요청은 410 `session_expired`를 반환한다. 완료 전에 성공한 장바구니 변경 요청을 동일한 `Idempotency-Key`와 동일한 내용으로 재전송하면 저장된 성공 응답을 반환하며, 장바구니가 다시 변경되지는 않는다. 동일한 키와 동일한 주문 요청을 다시 보내면 첫 주문 결과를 반환하며, 새 주문은 새 세션에서 시작한다.

2026-10-14 PR #43 병합 직후 `main`(`3cb8529`)의 Docker 환경에서 실제 프론트 → `/backend/` 프록시 → 백엔드의 상품 조회, 장바구니 변경, 모의 주문, 새 주문 및 주문 응답 유실 뒤 동일 요청 재확인을 검증했다. 이 검증은 2026-10-15 정책 결정의 동작 근거이며, 미정 정책의 검증까지 뜻하지 않는다.

**첫 시연 결정:** 첫 시연에서는 위 구현을 그대로 사용한다. 고정 17개 상품과 현재 가격, 실제 결제 없는 모의 주문, 한 세션당 주문 1건을 시연 범위로 정한다. 프론트는 서버 응답의 상품·가격·합계를 표시하고, 완료 후 새 주문은 새 세션을 만든다.

## A. 고정 상품과 옵션

현재 17개 상품은 모두 `available=true`다. 서버 가격은 원 단위이며 시연 중 상품·가격을 변경하는 관리자 기능은 없다.

| 분류 | 상품명(가격, 원) |
| --- | --- |
| 커피 | 아메리카노(3,500), 카페 라떼(4,200), 바닐라 라떼(4,700), 카페 모카(4,800), 카라멜 라떼(4,800), 카푸치노(4,300) |
| 음료 | 레몬 티(4,000), 초콜릿 라떼(4,500), 말차 라떼(4,900), 얼그레이 티(4,000), 복숭아 티(4,200) |
| 푸드 | 에그 샌드위치(5,500), 버터 크루아상(3,200), 플레인 베이글(3,500), 블루베리 머핀(3,800), 초콜릿 쿠키(2,800), 딸기 케이크(6,500) |

커피·음료는 `iced` 또는 `hot`을 선택하고 푸드는 온도를 `null`로 보낸다. 같은 상품·온도 항목의 수량은 1~20개이며, 합산 후 20개를 넘으면 해당 변경 전체를 거절한다. 장바구니 전체 수량·금액 한도는 현재 별도로 없다.

**결정 A:** 이 상품·가격·옵션·항목별 수량 한도를 첫 시연에 그대로 사용한다. 품절 상품을 시연할지는 별도로 정한다.

수량 한도를 바꾸기로 결정하면 백엔드 주문 스키마·합산 검사, 음성 요청 스키마, 프론트 주문 화면의 한도값을 함께 확인한다. 현재 값은 여러 모듈에 각각 정의돼 있으므로 문서만 바꿔서는 동작이 일치하지 않는다.

## B. 주문의 의미

주문 성공 응답은 `status=simulated`와 서버가 만든 주문번호, 확정 시점의 상품·금액 스냅샷을 담는다. 실제 결제, 결제 수단 연결, 재고 차감은 수행하지 않는다.

**결정 B:** 첫 시연은 실제 결제·재고 차감 없는 모의 주문 완료까지로 한다. 시연 화면에 “모의 주문”임을 어떻게 표시할지는 프론트 담당자가 확인한다.

현재 주문번호는 `SIM-` 뒤에 16진수 32자리가 붙는다. 완료 화면의 문구를 정할 때 실제 서버 응답으로 큰 글씨·낮은 화면에서 번호의 줄바꿈과 가독성을 확인하고, 표시 형식 변경이 필요하면 프론트·백엔드가 함께 결정한다.

## C. 세션당 주문 수와 완료 후 동작

한 세션에서 주문을 한 건 확정하면 그 세션의 장바구니 조회와 새로운 변경 요청은 410 `session_expired`로 거절한다. 이전에 성공한 장바구니 변경 요청을 동일 키·동일 내용으로 재전송하면 기존 성공 응답을 반환한다. 같은 키·같은 요청으로 주문 성공 응답도 재확인할 수 있다. 다른 키로 두 번째 주문은 만들 수 없고, 새 주문 버튼은 새 세션을 만든다.

**결정 C:** 이 완료·재시작 동작을 첫 시연 정책으로 채택한다. 주문 완료 뒤 특징 전송·음성 요청의 처리, 유휴 만료·완료 기록의 보관·복원은 이번 결정에 포함하지 않고 후속 안건에서 정한다.

현재 주문 완료 표시는 주문 모듈 안에 있고, 특징 전송·음성 요청은 세션 존재만 확인한다. 후속 안건에서는 주문 완료 상태를 두 요청과 자동 지원 판단이 같은 기준으로 읽을 방법을 함께 정한다. 또한 현재 프론트는 새 주문·새로고침 뒤에도 낮은 화면을 포함한 수동 화면 설정을 유지하고, 사용자가 ‘기본 화면’을 선택할 때 초기화한다. **같은 이용자의 새 주문**과 **다음 이용자 시작**을 어떻게 구분할지, 다음 이용자의 화면 설정을 언제 초기화할지도 별도로 합의한다. 이 문서는 두 동작의 정책을 확정하지 않는다.

## 리뷰와 결정 기록

영향받는 담당자는 변경 PR에서 A·B·C와 실제 화면·서버 동작의 일치 여부를 확인하고, 차이가 있으면 정확한 수정값을 남긴다.

```text

B 모의 주문 범위: 화면·서버와 일치 / 차이(정확한 범위)
C 한 세션 한 주문: 화면·서버와 일치 / 차이(완료·새 주문 동작)
다음 이용자의 화면 설정 초기화: 의견(초기화 시점·트리거) / 보류
추가 이유 또는 화면 영향:
```

| 결정일 | 참석·확인 담당 | A | B | C | 수정값·근거 | 후속 계약·구현 담당 |
| --- | --- | --- | --- | --- | --- | --- |
| 2026-10-15 | 백엔드 담당자(사용자 지시); 다른 담당자 확인은 변경 PR에서 요청 | 채택 | 채택 | 채택 | 기존 구현·2026-10-14 통합 검증 기준. 수정값 없음 | 계약·백엔드 문서: 백엔드 담당자; 화면 표시 확인: 프론트 담당자 |

A·B·C를 [API 검토 초안](Product-Cart-Order-API-Draft.md)과 OpenAPI의 해당 설명에 반영했다. 처리 중 중복 요청·재시도 간격, 공개 배포의 세션 접근 통제와 Supabase 저장 방식은 별도 안건으로 남긴다. 이 변경은 API 필드·경로·상태 코드나 실행 코드를 바꾸지 않는다.
