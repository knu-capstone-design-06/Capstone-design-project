# 첫 시연 상품·모의 주문·세션 정책 합의안

상태: **팀 검토용 제안 — 아직 확정되지 않음** (2026-10-14)

이 문서는 첫 시연의 주문 범위만 결정하기 위한 안건이다. PR 리뷰에서 아래 A·B·C를 **각각** 채택·수정·보류로 표시하고, 수정할 경우 정확한 값을 남긴다. 단순한 PR 승인이나 병합만으로 계약 확정으로 해석하지 않는다. 결정 날짜·참석자·결과를 이 문서에 기록한 뒤 [프론트↔백엔드 OpenAPI](../contract/frontend-backend.openapi.yaml)의 `x-contract-status: draft` 변경 여부를 별도 검토한다.

## 현재 구현과 제안

[PR #40](https://github.com/knu-capstone-design-06/Capstone-design-project/pull/40)의 백엔드는 [고정 카탈로그](../backend/app/modules/ordering/catalog.py)를 서버에서 제공하고, 장바구니의 옵션·수량·금액을 검증한다. 주문 확정은 실제 결제·재고 차감 없이 `simulated` 상태의 주문 스냅샷을 만든다. 한 세션의 주문 확정은 한 번만 허용하고, 완료된 세션의 장바구니 조회와 새로운 변경 요청은 410 `session_expired`를 반환한다. 완료 전에 성공한 장바구니 변경 요청을 동일한 `Idempotency-Key`와 동일한 내용으로 재전송하면 저장된 성공 응답을 반환하며, 장바구니가 다시 변경되지는 않는다. 동일한 키와 동일한 주문 요청을 다시 보내면 첫 주문 결과를 반환하며, 새 주문은 새 세션에서 시작한다.

2026-10-14 PR #43 병합 직후 `main`(`3cb8529`)의 Docker 환경에서 실제 프론트 → `/backend/` 프록시 → 백엔드의 상품 조회, 장바구니 변경, 모의 주문, 새 주문 및 주문 응답 유실 뒤 동일 요청 재확인을 검증했다. 이는 **현재 동작의 검증**이며 팀이 첫 시연 정책으로 채택했다는 뜻은 아니다.

**제안:** 첫 시연에서는 위 구현을 그대로 사용한다. 고정 17개 상품과 현재 가격, 실제 결제 없는 모의 주문, 한 세션당 주문 1건을 시연 범위로 정한다. 프론트는 서버 응답의 상품·가격·합계를 표시하고, 완료 후 새 주문은 새 세션을 만든다.

## A. 고정 상품과 옵션

현재 17개 상품은 모두 `available=true`다. 서버 가격은 원 단위이며 시연 중 상품·가격을 변경하는 관리자 기능은 없다.

| 분류 | 상품명(가격, 원) |
| --- | --- |
| 커피 | 아메리카노(3,500), 카페 라떼(4,200), 바닐라 라떼(4,700), 카페 모카(4,800), 카라멜 라떼(4,800), 카푸치노(4,300) |
| 음료 | 레몬 티(4,000), 초콜릿 라떼(4,500), 말차 라떼(4,900), 얼그레이 티(4,000), 복숭아 티(4,200) |
| 푸드 | 에그 샌드위치(5,500), 버터 크루아상(3,200), 플레인 베이글(3,500), 블루베리 머핀(3,800), 초콜릿 쿠키(2,800), 딸기 케이크(6,500) |

커피·음료는 `iced` 또는 `hot`을 선택하고 푸드는 온도를 `null`로 보낸다. 같은 상품·온도 항목의 수량은 1~20개이며, 합산 후 20개를 넘으면 해당 변경 전체를 거절한다. 장바구니 전체 수량·금액 한도는 현재 별도로 없다.

**검토 요청 A:** 이 상품·가격·옵션·항목별 수량 한도를 첫 시연에 그대로 사용할지 결정한다. 변경이 필요하면 상품 ID/이름/가격 또는 한도값과, 품절 표시를 시연에 사용할지 적는다.

## B. 주문의 의미

주문 성공 응답은 `status=simulated`와 서버가 만든 주문번호, 확정 시점의 상품·금액 스냅샷을 담는다. 실제 결제, 결제 수단 연결, 재고 차감은 수행하지 않는다.

**검토 요청 B:** 첫 시연을 모의 주문 완료 화면까지로 정하고, 실제 결제·재고 관리는 후속 범위로 둘지 결정한다. 시연 화면에 “모의 주문”임을 어떻게 표시할지도 프론트 담당자가 확인한다.

## C. 세션당 주문 수와 완료 후 동작

한 세션에서 주문을 한 건 확정하면 그 세션의 장바구니 조회와 새로운 변경 요청은 410 `session_expired`로 거절한다. 이전에 성공한 장바구니 변경 요청을 동일 키·동일 내용으로 재전송하면 기존 성공 응답을 반환한다. 같은 키·같은 요청으로 주문 성공 응답도 재확인할 수 있다. 다른 키로 두 번째 주문은 만들 수 없고, 새 주문 버튼은 새 세션을 만든다.

**검토 요청 C:** 이 완료·재시작 동작을 첫 시연 정책으로 채택할지 결정한다. 주문 완료 뒤 특징 전송·음성 요청의 처리, 유휴 만료·완료 기록의 보관·복원은 이번 결정에 포함하지 않고 후속 안건에서 정한다.

## 리뷰와 결정 기록

프론트엔드와 백엔드 담당자는 PR에서 다음 형식으로 의견을 남긴다.

```text
A 상품·가격·옵션·수량: 채택 / 수정(정확한 값) / 보류
B 모의 주문 범위: 채택 / 수정(정확한 범위) / 보류
C 한 세션 한 주문: 채택 / 수정(완료·새 주문 동작) / 보류
추가 이유 또는 화면 영향:
```

| 결정일 | 참석·확인 담당 | A | B | C | 수정값·근거 | 후속 계약·구현 담당 |
| --- | --- | --- | --- | --- | --- | --- |
| 미정 | 미정 | 미정 | 미정 | 미정 | 미정 | 미정 |

A·B·C가 모두 합의되면 결정 기록을 갱신하고, [API 검토 초안](Product-Cart-Order-API-Draft.md)과 OpenAPI의 관련 문장·예시를 프론트·백엔드 담당자가 함께 확인한다. 부분 합의는 부분 합의로 기록하며, 처리 중 중복 요청·재시도 간격, 공개 배포의 세션 접근 통제와 Supabase 저장 방식은 별도 안건으로 남긴다. 이 PR은 API 형식이나 실행 코드를 변경하지 않는다.
