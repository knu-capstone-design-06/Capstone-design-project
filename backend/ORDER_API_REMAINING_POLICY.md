# 주문 API 잔여 정책: 첫 시연 범위와 후속 검토

상태: **백엔드 담당자의 첫 시연 범위 결정 · 교차 담당 검토 요청** (2026-10-17). 이 문서는 [첫 시연 A·B·C](../docs/Order-API-First-Demo-Policy-Proposal.md)를 보완한다. 프론트·AI 담당자가 영향을 받는 410 응답은 검토 전 제안이며, 이 파일 추가만으로 OpenAPI나 서버 동작이 바뀌지 않는다. 주문 API의 `x-contract-status: draft`도 유지한다.

## 첫 시연에 채택한 범위

| 항목 | 첫 시연 정책 | 현재 구현과 차이 |
| --- | --- | --- |
| 저장·접근 | 현장 또는 통제된 내부망의 비공개 단일 백엔드 프로세스에서 진행한다. 세션·Cart·주문·성공 키는 프로세스 메모리에만 보관한다. 재시작 후 복원은 제공하지 않는다. | 현재 코드와 같음. 백엔드 재시작 뒤 기존 세션 요청은 404가 된다. |
| 성공 요청 재전송 | 같은 세션·`Idempotency-Key`·메서드·경로·쿼리·본문이면 저장된 성공 응답을 재사용한다. 같은 키로 다른 요청을 보내면 409 `idempotency_key_reused`다. 완료 세션에서 이미 성공한 변경·주문 요청을 재전송해도 Cart나 주문을 다시 바꾸지 않는다. | 현재 코드와 같음. 재사용 보장은 프로세스가 살아 있는 동안에 한정된다. |
| 처리 중 중복 | 단일 프로세스 잠금으로 변경을 순서대로 처리한다. 시연용 주문 API에 별도 `request_in_progress` 또는 `Retry-After`를 추가하지 않는다. | 현재 코드와 같음. 음성 API의 별도 `request_in_progress`는 이 결정으로 변경하지 않는다. |
| 유휴·시간 만료 | 시연 중 임의의 시간 만료를 새로 적용하지 않는다. 주문 완료의 Cart 410과 시간 만료를 구분한다. | 현재 코드와 같음. 실행 중 세션/결과가 시간만으로 정리되지 않으므로 비공개 단일 서버 시연에만 허용한다. |
| 주문번호 | 현재 `SIM-` + 대문자 16진수 UUID 32자리의 화면 표시값을 유지한다. 내부 `order_id`와 구분한다. | 현재 코드와 같음. 형식 변경은 프론트 완료 화면과 함께 검토한다. |

`session_id`는 공개 인터넷의 소유권 증명이 아니며 CORS는 인증·인가가 아니다. HTTPS 진입점을 마련하더라도 아래 공개 배포 조건을 완료하기 전 Cart/Order API를 무제한 공개하지 않는다. 첫 시연이 비공개 범위를 벗어나면 이 정책을 다시 검토한다.

## 완료 세션의 특징·음성 요청: 교차 담당 검토안

백엔드 담당자는 주문 완료 뒤 **새 특징 전송**(`POST /api/v1/sessions/{session_id}/features`)과 **새 음성 요청 접수**(`POST /api/v1/sessions/{session_id}/voice/requests`)를 410 `session_expired`로 거절하는 방향을 채택했다. 이는 A·B·C의 한 세션 한 주문과 일관되지만, 현재 두 서비스는 세션 존재만 확인해 완료 뒤에도 접수한다. 코드나 공용 계약은 아직 바꾸지 않았다.

적용 시 경계는 다음과 같다.

- 이미 접수된 음성 요청의 `GET /api/v1/sessions/{session_id}/voice/requests/{request_id}` 결과 조회는 주문 완료 뒤에도 허용한다. 진행 중인 응답을 확인할 길을 남긴다.
- 완료 전에 접수된 동일 `Idempotency-Key`·동일 음성 요청의 재전송을 접수 결과 재생으로 처리할지, 410으로 처리할지는 프론트·AI 담당자와 정한다. 서로 다른 본문에 같은 키를 재사용하는 요청은 기존 충돌 규칙을 유지한다.
- 완료 판정은 주문 모듈 내부에서만 읽지 않고 특징·음성 서비스도 일관되게 확인할 수 있어야 한다. 저장소 전환 시 같은 상태를 DB 트랜잭션에서 읽는다.
- 410의 JSON 오류 형식은 기존 특징 API(`HTTPException.detail`)와 음성 API(`{code, detail}`)가 다르므로 각 계약에 정확한 예시를 적는다. 통일 여부를 이 문서만으로 결정하지 않는다.

프론트는 주문 완료 후 새 특징/음성 요청을 멈추고, 410을 받았을 때 새 세션 시작 경로로 안내하는지 검토한다. AI 담당자는 음성 접수·조회 및 처리 중인 요청의 상태 전이에 영향이 없는지 검토한다. 검토가 확인되면 `contract/frontend-backend.openapi.yaml`과 `contract/voice.openapi.yaml`, 백엔드 코드·테스트를 같은 PR 범위에서 반영한다.

## 공개 배포 전에 별도로 완료할 조건

1. Supabase에 세션·Cart·주문 스냅샷·성공 키/응답을 보관하고, 상태 변경과 멱등성 기록을 한 트랜잭션으로 처리한다. `kiosk_backend` 역할에는 필요한 테이블만 최소 권한을 추가한다. 기존 병합 마이그레이션은 수정하지 않는다.
2. 세션 접근 주체(단말 인증 또는 그에 준하는 방식), 유휴 만료·완료 뒤 재확인 기간, 주문·음성·키 보관 및 삭제 시간을 결정한다. 종료된 세션의 오래된 키가 새 주문으로 재실행되지 않게 한다.
3. DB/다중 인스턴스에서 동일 키 경합을 한 번만 실행하도록 보장한다. 처리 중 응답을 쓴다면 `409 request_in_progress`의 본문·`Retry-After` 간격을 프론트와 합의하고 계약에 추가한다. 성공/실패 결과의 보관·재전송 규칙도 함께 결정한다. 현재 주문 API는 이 상태 코드와 헤더를 반환하지 않는다.
4. 재시작·동시 요청·응답 유실·DB 장애와 백업 복구를 검증한 뒤 공개 배포한다. 실제 결제·재고 차감은 첫 시연과 별개다.
